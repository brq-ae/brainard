# 0019 — Getting Data Out: Room-Setup and Doctrine Copy Briefings for External LLMs, and a Collapsible New-Room Form

- **Status:** accepted
- **Date:** 2026-09-10

## Context and Problem Statement

Every prior room-page ADR has been about getting information *into* Brainard or moving it *between* rooms and the library (ADR-0011's export/AI-actions, ADR-0013's copy buttons). The owner now wants the reverse: three ways to get information *out* of Brainard and into somewhere it isn't connected — a browser-based external LLM conversation (Gemini, ChatGPT) that cannot reach the Brain, or simply onto his clipboard.

Three concrete needs, settled with the owner:

1. The "New room" form on `/ui/rooms` (`app/templates/rooms_list.html`) sits above the room list, so the owner scrolls past a full create-room form every time he only wants to look at existing rooms.
2. When the owner is already mid-conversation with an external LLM about some topic (his example: a contract) and wants to turn that conversation into a Brainard room, he currently has to manually translate the discussion into the create-room form's fields himself, field by field, with no help from the LLM he's already talking to.
3. The owner wants to paste Brainard's current doctrine into a *separate* web LLM conversation (his example: Gemini) that cannot reach the Brain, so that LLM adopts the same operating rules for that conversation.

Two hard constraints surfaced during review, each materially reshaping one decision below. First (decision 2): the owner does not want any external LLM to learn anything about his infrastructure — no machine names, no agent names, no group names, no project names, not even as illustrative examples. The real workflow is narrower than "brief an external LLM to propose a full room configuration": he pastes a short, generic, context-free instruction into an LLM he's already talking to, gets back a filled-in block for what that LLM *can* infer from the conversation it's already having (name, mode, topic, message/consensus bounds, time limit), and fills in everything Brainard-specific himself (the two agent names, group, project) directly in the form, same as he does today. Second (decision 4): he does not want the doctrine copy to hand an external LLM rules it structurally cannot follow (depositing to the Brain, searching it, and the like) — only the subset that's genuinely about conduct.

## Decision

### 1. The "New room" form becomes collapsible, default collapsed

The form (`rooms_list.html:11-136`) is wrapped in a `<details>` element so the room list below it (`rooms_list.html:184-225`) is visible without scrolling past a multi-field form — following the collapsible-transcript precedent (ADR-0013 decision 7: a `<details>` element with a live count in its header, reusing an already-fetched value rather than adding a second counter).

**Default: collapsed.** The whole point of this change is seeing the list first; a form the owner opens deliberately, rather than one he closes every visit, matches that. This is the opposite default from ADR-0013 decision 7's transcript (open by default, since the transcript *is* the room page's main content) — the two are different content with different defaults for the same reason: each defaults to whatever is the primary reason to be on that page.

**Live count in the `<summary>`**, following the same discipline ADR-0013 decision 7 states for its own count ("reuses that same element/update path, it does not add a second counter that could drift from it"): the count is `rooms|length` — the same list already fetched for the "Rooms" panel just below, not a second query. This is honestly page-bound (it counts the current page of up to `ROOM_LIST_LIMIT` rooms, like every other figure on this page already is — there is no existing total-room-count query anywhere in `app/rooms.py` to reuse, and adding one solely to decorate a `<summary>` would be a second, independently-queried number with its own drift risk, the exact thing ADR-0013's own discipline warns against). Rendered as e.g. `Show new-room form (20 rooms below)`.

**Heading and the new "Copy room-setup briefing" button (decision 2) live outside the `<details>`, not inside its `<summary>`.** Two reasons: (a) an interactive `<button>` nested inside a native `<summary>` risks its click also toggling the disclosure (the `<summary>` itself is the whole element's default click target) — keeping them as siblings avoids that entirely, no JS event-handling gymnastics needed; (b) the owner may want the format-spec briefing (decision 2) without ever opening the form — it is now a generic, context-free spec (see decision 2), reasonably grabbed early in an external conversation, before the owner has any intention of opening the create-room form at all. Structure: `<div class="panel-header"><h2>New room</h2><button data-copy-target="...">Copy room-setup briefing</button></div>` immediately followed by the `<details>` wrapping the existing form fields, unchanged.

**The form's existing behaviour is otherwise untouched**: same fields, same `action="/ui/rooms"`, same validation, same error re-render path (`rooms_create`'s `except ApiError` branch, `app/routers/ui_rooms.py:585-622`). `<details>` is a native, unscripted disclosure widget — no JS is added for the collapse/expand behavior itself (same posture ADR-0013 decision 7 and ADR-0012's existing "Join prompts" section already established for this exact element).

### 2. "Copy room-setup briefing" — a generic, zero-fleet-data format spec, not a fleet briefing

**Revised from the original framing during review, per explicit owner correction.** The original design generated a briefing from live fleet data (active machines, groups, projects) so an external LLM could propose a complete configuration including which real agents to assign. The owner rejected this outright: *"I dont want any external agent to know anything about my machines etc. just understand the format."* His actual workflow: he's mid-conversation with an external LLM about some topic that knows nothing about Brainard and that he does not want to explain to it. He pastes a short, generic instruction ("format what we've discussed into this structure"), the LLM emits the block from context it already has, and he pastes that block into the create-room form. Anything the LLM cannot know, he fills in himself, by hand, exactly as he does today.

**What the button copies is therefore a pure format spec — a description of the shape and constraints of a room configuration, with zero fleet data of any kind: no machine name, no agent name, no group name, no project name, not even as an illustrative example.** Concretely, it explains:

- What Brainard is and what a "room" is, in the minimum terms needed to make sense of the fields below — one or two sentences, not an architecture explainer: a private multi-agent system; a room is a structured, bounded chat session between two already-connected AI agents working through a topic, shaped by a "mode." No URLs, no endpoints, no mention of how rooms are created or what API backs them.
- The valid modes and what each means, generated from `app/room_modes.py`'s `ROOM_MODES` (the single source of truth already used by the create-room form itself, `_ROOM_MODES_PAYLOAD`/`ROOM_MODES_JSON` in `app/routers/ui_rooms.py:214-226`) — for each mode: its label, whether it's symmetric (freeform, collaborate, brainstorm — no sides, no adversarial framing) or asymmetric-with-sides (debate: For/Against; critique: Proposer/Critic), and that for an asymmetric mode, whichever agent name ends up first is assigned the mode's first side (mirroring `_sides_for_mode`'s actual ordering rule, `app/routers/ui_rooms.py:231-246`). This is product behavior, not a fleet fact — safe and necessary to state precisely so the format spec doesn't drift from what `create_room` (`app/rooms.py`) actually enforces.
- Each field's meaning and real constraint, generated from `app/rooms.py`'s own validator constants — never restated as separate hand-maintained prose with its own numbers:
  - `name` — required, non-empty.
  - `mode` — one of the modes just described; default `freeform` (`DEFAULT_MODE`).
  - `topic` — required and non-empty for every mode except freeform (`_validate_topic`); ignored (optional) for freeform.
  - `agent_a` / `agent_b` — **leave blank.** These are the room's two participants, drawn from the owner's own registered agents; the spec states plainly that the receiving LLM has no way to know their names and must not guess or invent placeholders — the owner fills these in himself, in the form, after pasting.
  - `max_messages` — an integer between `MAX_MESSAGES_MIN` and `MAX_MESSAGES_MAX` (1-10000), default `DEFAULT_MAX_MESSAGES` (100) if left blank.
  - `consensus_floor` — an integer between `CONSENSUS_FLOOR_MIN` and `CONSENSUS_FLOOR_MAX` (1-10000), default `DEFAULT_CONSENSUS_FLOOR` (20) if left blank; stated plainly that it only has an effect for debate/critique rooms (must be strictly less than `max_messages` there — `create_room`'s `consensus_floor_unreachable` check, `app/rooms.py:425-433`) and is otherwise stored but ignored.
  - `group` — **leave blank**, with a generic (no real examples) explanation of what it's for: an owner-facing free-form label used only to filter and bulk-manage the owner's own room list; it has no effect on the room's conversation and the receiving LLM cannot know what labels the owner already uses.
  - `project` — **leave blank**, with a generic explanation: a free-form identity string the owner's own agents compare, exactly, against their own current work before joining a room, as a safety check (ADR-0018's join-prompt target block) — the receiving LLM cannot know the owner's project naming, and guessing one risks a real agent later being told, correctly, to stop and not join.
  - Time limit — either no limit, or a duration, bounded `MIN_DURATION_SECONDS`-`MAX_DURATION_SECONDS` (1 second to 30 days) — expressed to the LLM as whole minutes for simplicity, since that's what a conversation is likely to imply ("give them an hour to hash this out").
- The fixed reply format (decision 3) and an explicit instruction to fill in what can genuinely be inferred from the conversation already underway (name, mode, topic, and — only if the conversation implies them — `max_messages`/`consensus_floor`/the time limit) and to leave every other field's value blank rather than invent, guess, or placeholder one.

**Generated from the code's own constants, not hardcoded prose — but now with zero DB access.** Because nothing in this text varies per request (it depends only on `ROOM_MODES` and `app/rooms.py`'s module-level validator constants, never on any database row), it is computed **once, at import time**, as a module-level constant in a new small module, `app/room_setup_briefing.py` — exactly the same "static, trusted, never per-request" posture `ROOM_MODES_JSON` already has (`app/routers/ui_rooms.py:214-226`, "computed once at import time -- the data is static/trusted"). This is a meaningful simplification over the original fleet-aware design, which would have needed the already-fetched `active_machines`/`groups`/`project_names` threaded through as parameters (mirroring `render_transcript_markdown`'s shape); a zero-argument, import-time constant has no such plumbing and cannot leak a stale value between requests because there is no per-request value at all.

Anti-drift property preserved despite the removal of live data: a future change to `MAX_MESSAGES_MAX`, a new room mode, or a changed consensus-floor rule flows into the next-served copy of this text automatically (well, on next process restart, since it's computed at import time — the same freshness bound `ROOM_MODES_JSON` already accepts). What does **not** auto-update is the hand-written English framing around each constant (e.g., the sentence explaining *why* `consensus_floor` must be less than `max_messages`) — that prose still has to be kept honest by whoever changes the underlying rule, the same category of risk every other generated-prompt docstring in this codebase already carries (`app/onboarding.py`'s generators are the precedent: numbers and enums are single-sourced and can't drift, but the sentences wrapping them are still hand-maintained).

Rendered into the page as a hidden container (`<pre id="room-setup-briefing-text" hidden>{{ room_setup_briefing }}</pre>`) with the button from decision 1 reading `data-copy-target="room-setup-briefing-text"` — same "compute the text server-side, expose it via a hidden element's `.textContent`, let the existing click handler read it" pattern `transcript_md` (ADR-0011) and `join_prompts` already use, and per decision 5, the same shared `[data-copy-target]` click handler, no new copy path.

### 3. The reply format, and the "paste setup" box that parses it

**Format: a sentinel-delimited, fenced key: value block**, versioned:

```
BRAINARD-ROOM-SETUP-v1
name: <value or blank>
mode: <value or blank>
topic: <value or blank>
agent_a: <leave blank>
agent_b: <leave blank>
max_messages: <value or blank>
consensus_floor: <value or blank>
group: <leave blank>
project: <leave blank>
duration_minutes: <value or blank>
END-BRAINARD-ROOM-SETUP
```

The briefing tells the LLM to wrap this in a fenced code block (```` ``` ````) for readability, but the **sentinel lines are the real delimiter**, not the fence — robust to an LLM that adds a paragraph of commentary before or after the block, or that renders the fence slightly differently. This mirrors two existing precedents in this codebase rather than inventing a new convention: `app/routers/bootstrap.py`'s `TEMPLATES` dict (fixed, fenced fill-in-the-blank templates for `handoff`/`lesson`/`howto`) for the "give the fenced template, expect it echoed back filled in" shape, and ADR-0011 decision 4's nonce-delimited transcript framing for the "an explicit, hard-to-spoof-by-accident delimiter is what makes untrusted text parseable" principle. Ten fixed keys, no nesting — deliberately not JSON: an LLM asked for JSON is more likely to mangle quoting/commas/trailing commas than to mis-type a `key: value` line, and a line-oriented format needs no JSON parser to fail safely on.

**Parsing happens client-side, in a new file, `app/static/room_setup_paste.js`** — not server-side. Justification:

- It only ever needs to populate the exact same `<input>`/`<select>` elements the owner would otherwise type into by hand — no new server endpoint, no new response contract, no new schema. This is the same "UI layer resolves shape, the one domain function validates" split `app/routers/ui_rooms.py` already documents repeatedly for this exact form (`_sides_for_mode`, `_parse_duration_seconds`: "nothing about mode/topic/side/duration validity is re-checked here beyond what's needed to resolve the form's shape into that function's plain parameters") — just carried out in the browser instead of in the router, because there is no server round trip needed to fill in a form the browser already has every piece of.
- Fast, round-trip-free feedback for what is fundamentally a copy-paste formatting problem (an LLM not following instructions exactly), not a domain-validation problem — bouncing the owner through a full page reload to discover "the LLM replied in prose" would be a worse experience than an inline message that appears instantly.
- The server-side domain function, `create_room` (`app/rooms.py`), is **completely unchanged** by this feature and remains the sole authority on real validation (ranges, the `consensus_floor_unreachable` cross-check, member/topic requirements) — a paste-filled form is submitted through `POST /ui/rooms` exactly like a hand-filled one, and any semantic/range problem the structural parser didn't catch is reported by the existing `rooms_create` → `except ApiError` → re-render-with-error path, unchanged.

**Parser behavior — structural, all-or-nothing, and never a silent partial or wrong fill:**

1. Search the pasted text for exactly one `BRAINARD-ROOM-SETUP-v1` … `END-BRAINARD-ROOM-SETUP` sentinel pair (leading/trailing prose or a surrounding code fence is tolerated; the sentinels themselves must match exactly). **Not found at all** → hard failure: "Couldn't find a BRAINARD-ROOM-SETUP-v1 … END-BRAINARD-ROOM-SETUP block in the pasted text. Paste the LLM's exact reply to the copied briefing, unedited — plain prose or a differently-shaped answer won't parse." **Found more than once** → hard failure naming that ambiguity ("found more than one block; paste only the LLM's final answer"). Either way, **no form field is touched.**
2. Every non-blank line between the sentinels must match `key: value`. A line that doesn't → hard failure quoting the offending line verbatim.
3. Every key must be one of the fixed ten. An unrecognized key → hard failure naming it — **unknown keys are never silently ignored**, since silently dropping a key the owner expected to be honored is itself a silent partial acceptance.
4. A key appearing twice → hard failure naming the duplicate.
5. `name` and `mode` must be non-blank; `topic` must be non-blank whenever `mode` resolves to anything other than `freeform`. Any of these blank when required → hard failure naming which.
6. `mode`, if given, must match one of the five known mode keys (checked against the same `ROOM_MODES_JSON` payload already embedded on this page for `room_form.js`, `app/routers/ui_rooms.py:214-226` — no second, divergent mode list) → otherwise a hard failure listing the valid set.
7. `max_messages`/`consensus_floor`/`duration_minutes`, if non-blank, must be plain integers → otherwise a hard failure quoting the bad value. (Only a *type* check — range is deliberately left to `create_room`, per the justification above.)
8. **A blank or omitted value for any key — including `agent_a`, `agent_b`, `group`, `project`, and the optional numeric/duration fields — is legitimate, not an error, and means "leave this form field exactly as it is."** This is the field-level counterpart to the format's own design: `agent_a`/`agent_b`/`group`/`project` are expected to arrive blank every time (decision 2 tells the LLM to leave them so), and the parser must not clear or default those fields just because the reply is silent on them — the owner fills them in himself, in the plain form fields, same as always, either before or after pasting.
9. Any other case is success: the non-blank fields are written into their form elements, a `change` event is dispatched on each so `room_form.js`'s existing listeners re-run (`updateAgentLabels`/`updateTopicRequired`/`updateCustomDurationVisibility`, `app/static/room_form.js:82-95`) and stay in sync rather than being duplicated here, the `<details>` from decision 1 is programmatically opened (`detailsEl.open = true`) so the now-filled form is immediately visible, and a plain confirmation appears ("Parsed — review the filled-in fields, then fill in the agent names, group, and project yourself before creating the room.").

Every failure path replaces any previous message (no stale errors linger) and touches zero form fields — parsing is atomic: fully validated structurally before anything is written, or nothing is written at all.

**The paste box never auto-submits the form.** The owner reviews, fills in the fields the parser deliberately left alone, and clicks "Create room" himself — the same "review before it becomes real" discipline ADR-0011 decision 3 established for AI-action results ("Nothing is written automatically").

### 4. "Copy doctrine" — a checklist of whole rules, not the full rulebook, with an explicit per-rule portability marker

A "Copy doctrine" button and rule checklist on the doctrine UI page (`/ui/doctrine`, `app/templates/doctrine.html`) only — not the rooms page. This is the owner's own doctrine text, which he is knowingly and deliberately choosing to paste somewhere external (his example: a Gemini conversation) — a different category from decision 2's briefing, which now carries no information the owner didn't explicitly choose to put in the box himself.

**Revised from the original proposal during a second round of review.** The original design copied the entire compiled global doctrine verbatim. The owner rejected that too, for a different reason than decision 2's: *"it doesn't need to do the rules that it cant [follow], like deposit etc. just the doctrines that will make it helpful like never assume etc."* Most of Brainard's doctrine is written for a session that has Brain access and runs on a registered machine — instructions to a disconnected browser LLM to, say, "deposit a handoff" are not just unhelpful, they're actively confusing (an LLM told to do something it structurally cannot do has no good way to react to that). Only the rules whose substance is about *conduct* — how to behave, independent of what tools are available — genuinely translate.

**Point-in-time assessment of the current 12 global rules, recorded here for context, not encoded anywhere in code:** the owner assesses that **G1** (never assume/guess — stop and ask), **G2** (never execute beyond what was agreed), **G3** (agree before implementing), and **G12** (never end a turn on a bare announcement of intent) are conduct rules that hold with zero Brain access or fleet membership. The other eight are structurally inapplicable outside Brainard for reasons specific to each: G4 concerns the Brain's supersede-never-erase knowledge store; G5 needs git; G6 requires depositing a handoff; G7 requires searching the Brain; G8's mirror requires `documents[]` deposits; G9 needs notification hooks running on a registered machine; G10 presumes owner-assigned Commander/Builder fleet roles; G11 needs the wrapper's fetch/cleanup verbs. **This four-rule split is deliberately not hardcoded anywhere** — see below for why, and for what carries it instead.

**Why not hardcode the split, and what replaces it: an explicit, owner-authored, per-rule marker — not a UI-side heuristic.** Doctrine is owner-authored and expected to grow (a future G13 is not a hypothetical); hardcoding today's four rule ids into application code would work perfectly until the day a new rule is added and silently miss it — exactly backwards from the "generated from the same constants/validators, never restated" discipline this ADR follows everywhere else (decisions 2 and elsewhere in this section). Two ways to determine "portable to an external LLM" without hardcoding ids were weighed:

- **A UI-side default with no new data** — e.g., the checklist always starts with nothing checked (safe, but gives the owner no head start every single time he uses this) or always starts fully checked (defeats the entire point of this correction). Either way, a rule the code has never seen before — including every rule that exists *today*, before any marker is introduced — has no basis for its default state beyond a guess the UI author made once, in the abstract, with no information about that specific rule's content. **Stated plainly, as the owner asked: a newly added rule under this option would appear in some default state nobody actually chose deliberately for it** — full-text-scanning the rule for keywords like "deposit" or "Brain" was also considered and rejected as a third variant of this same problem, just a fuzzier, even-more-fragile version of guessing from the outside.
- **An explicit `external_safe: bool` field on each rule, authored by the owner at the same moment he writes the rule's `tier`/`text`** (`DoctrineRuleIn`, `app/schemas.py:225-234`, currently `id`/`tier`/`text` only) — the same person who already makes an explicit, per-rule judgment call about `tier` (non-negotiable vs. default — nothing infers that from the rule's text either) makes an equally explicit judgment call about portability, at authoring time, as part of the same act. A future G13 is simply given (or not given) this field the moment it's written; there is no separate step to remember and no code to update when the rule set changes.

**Decision: the marker is the real, adopted design, not merely a considered alternative** — it is the only one of the two that actually satisfies "sensible default, never hardcoded, never silently stale," the property the owner asked for. `DoctrineRuleIn` gains one new field, `external_safe: bool = False` — **omitted or unset defaults to `False` (excluded)**, the fail-closed direction: a rule nobody has yet made a deliberate call about is treated as *not* safe to hand to an outside LLM, never the reverse. This is a genuinely new field on the doctrine rule shape (`app/schemas.py`'s `DoctrineRuleIn`, threaded through `_validate_global_rules`/the stored `rules` JSON/`_compile_doctrine`/the UI doctrine page's rule rendering — the same "pass the field along unchanged" shape `id`/`tier`/`text` already have everywhere).

**Cost, stated honestly, since this is a real one and the owner should see it before it's built:** (a) a small, additive, backward-compatible schema change — an old caller of `POST /v1/doctrine/global` that omits the field still works, defaulting every rule closed; (b) the owner's **current** 12 rules were all authored before this field existed, so none of them has `external_safe: true` yet — the checklist would start with **nothing preselected** until the owner does a one-time doctrine re-authoring pass: a fresh `POST /v1/doctrine/global` (a normal, expected doctrine version bump — doctrine is already supersede-never-erase and versioned, exactly built for this kind of evolution, not a special migration) resubmitting his 12 rules with `external_safe: true` set on the four he named above (or however many he judges, going forward). Until he does that, the feature still works safely (an all-unchecked checklist the owner fills in by hand every time is exactly decision 4's *original*, pre-correction fallback behavior) — it simply isn't "sensible" yet in the way he asked for; that only materializes once he deliberately tags his own doctrine.

**The checklist itself:** for every rule in the current compiled global doctrine (`non_negotiable` and `default` tiers both eligible — tier governs whether a *project overlay inside Brainard* may override a rule, which is orthogonal to whether the rule is meaningful *outside* Brainard entirely; G2, for instance, is non-negotiable and squarely portable), render one checkbox per rule, `checked` set to exactly that rule's own `external_safe` value — `{% for r in all_global_rules %}<input type="checkbox" checked="{{ r.external_safe }}" data-rule-text="{{ r.text }}"> {{ r.id }} — {{ r.text }}{% endfor %}`, generic over however many rules exist and however they're tagged, no rule id ever named in the template or in code. A small new script, `app/static/doctrine_copy.js`, listens for `change` on the checklist and rebuilds the hidden `data-copy-target` element's `.textContent` from exactly the currently-checked boxes' `data-rule-text` values, each copied whole and unaltered — **rules are included or excluded, never paraphrased or trimmed to fit**; the initial page load already renders the hidden element correctly from the server-computed default-checked set, so a copy before ever touching a checkbox works with zero JS execution, and per decision 5 this is additive to, not a replacement of, the shared `[data-copy-target]` click handler in `app/static/main.js` (unmodified).

**What's copied — framing, version, and the whole-rule guarantee, stated explicitly:** the copied block opens by telling the receiving LLM these are operating rules to adopt for the remainder of this conversation, and — new in this revision — that it is **deliberately receiving a subset** of a larger doctrine ("the rules below are the ones that make sense without access to my system; the absence of a rule here doesn't mean it doesn't apply elsewhere, only that it doesn't translate to a conversation like this one"), so it never infers meaning from what's missing. It states the doctrine version it came from (`global:v{{ global_row.version }}`) so the owner can always tell what a given paste was based on. Every included rule's `text` is copied verbatim from the live `DoctrineVersion` row — never edited, summarized, or partially quoted on the way out.

**Why global doctrine only, not a compiled per-project view — unchanged from the original proposal:** `app/routers/bootstrap.py`'s `_compile_doctrine` merges global + one project's overlay, the right shape for a specific project's session bootstrap but wrong here — an external LLM conversation isn't scoped to one Brainard project, and pasting a project-specific override into an unrelated conversation would misrepresent it as universal. The checklist and copy text are built from `non_negotiable`/`default_rules`/`global_row.content`/`global_row.version`, the same rows `app/routers/ui_doctrine.py:30-34` already fetches — no new query for the *data*, only the new `external_safe` field riding along on rows already read. When no global doctrine has ever been posted (`global_row is None`), the whole checklist/button is omitted, matching the page's own existing `{% if not global_row %}` empty state.

**Owner-only, with no new gating code.** `/ui/doctrine` is already entirely behind `require_ui_session` (owner cookie only, `app/routers/ui_doctrine.py:27`) — the same posture every `/ui/*` page has. This is at least as strict as `GET /v1/doctrine`'s own separate owner gate (`require_owner`, `app/routers/doctrine.py:72`); no new authorization logic is added anywhere by this decision.

### 5. All three copy actions reuse the existing three-tier clipboard handler, unchanged

Per ADR-0013 decision 5's three-tier fallback (`navigator.clipboard` → hidden `<textarea>` + `execCommand('copy')` → `window.prompt`, `app/static/main.js:19-129`) — the owner reaches this UI over plain HTTP by LAN IP, never a secure context, so tier 1 never fires here either. Both new copy buttons this ADR adds (`room-setup-briefing-text`, decision 2; `doctrine-briefing-text`, decision 4) are ordinary `[data-copy-target]` buttons pointing at a hidden element's `.textContent`, exactly like every copy button before them (transcript export, join prompts). **No second copy path is written**, and `app/static/main.js` itself is not modified by this ADR at all — decision 3's paste box is not a copy action and has no clipboard involvement in the other direction; it only reads from a `<textarea>` the owner pastes into by hand.

## Alternatives Considered

- Generating decision 2's briefing from live fleet data (active machines, groups, projects) so an external LLM could propose a complete, ready-to-submit configuration including real agent assignments — this was the original design, **rejected by the owner outright** during review: "I dont want any external agent to know anything about my machines etc." A generic, zero-fleet-data format spec, with the owner filling in everything Brainard-specific by hand, is what ships instead (decision 2).
- A `ForeignKey`-validated `project`/`group` reference so the paste format could reject an unknown value outright — moot: the paste format never carries a `group`/`project` value in the first place (the LLM is told to leave them blank), and `Room.group_name`/`Room.project` are themselves free-form by prior, owner-approved design (ADR-0008, ADR-0018 decision 12) — nothing here reopens that.
- JSON instead of `key: value` lines for the reply format — rejected: an LLM asked for strict JSON is more likely to produce subtly invalid JSON (trailing commas, smart quotes, unescaped internal quotes) than to misformat a plain line, and a line-oriented format degrades to an obvious, quotable parse error rather than an opaque JSON syntax error.
- Server-side parsing of the pasted block (a new `POST /ui/rooms/parse-setup` endpoint returning field values as JSON for the page to apply) — rejected: adds a new endpoint and a round trip for a problem that is purely "fill in a form the browser already has every piece of," with no validation benefit over client-side parsing, since `create_room` remains the real authority either way (see decision 3's justification).
- Treating a blank `agent_a`/`agent_b`/`group`/`project` value as a parse error (forcing the owner to explicitly acknowledge each one) — rejected once decision 2 changed: blank is now the *expected, correct* value for those four fields on every successful parse, so treating it as an error would make the common case always fail.
- Putting "Copy doctrine" on the rooms page as well as the doctrine page — rejected: would require fetching global doctrine rows into `_room_context`/`rooms_list` for a feature unrelated to rooms, a second data-fetch path for the exact same content the doctrine page already renders natively.
- A compiled-per-project doctrine copy (reusing `_compile_doctrine`) instead of global-only — rejected; see decision 4 (misrepresents a project-scoped override as universal to a conversation that isn't scoped to any one project).
- Copying the entire compiled doctrine verbatim, unfiltered — the **original** proposal for decision 4, **rejected by the owner** in a second round of review: most rules instruct behavior (depositing, searching the Brain, notification hooks) a disconnected external LLM structurally cannot perform, which is actively confusing rather than merely inapplicable to hand it.
- Hardcoding today's four-rule "portable" split (G1/G2/G3/G12) directly in application code — rejected: would work only until the next rule is added, silently missing it; the entire reason this ADR reaches for a data-carried marker instead.
- A pure UI-side default preselection with no new data (e.g., the checklist always starts empty, always starts full, or a rule's default is guessed by scanning its text for keywords like "deposit"/"Brain") — rejected: every variant leaves a rule — including, on day one, every rule that currently exists — in a default state nobody deliberately chose for it specifically; keyword-scanning is the same problem in a fuzzier, more fragile form. An explicit, owner-authored `external_safe` field carries a real, deliberate decision instead of a guess.

## Consequences

- **No database migration, but one real schema/contract change.** `DoctrineVersion` itself is untouched — `rules` is already a JSON column with no fixed shape enforced by the database, so adding a key to the objects stored inside it needs no alembic revision at all (nothing to add to `alembic/versions/`; `0019_room_seat_binding_and_project.py` already exists for ADR-0018's own, separate migration — alembic revision numbers and ADR numbers are two independent sequences in this repo, confirmed by inspection before writing this document; this document's "0019" is the ADR sequence, unrelated to that migration file). What **does** change is the pydantic contract: `DoctrineRuleIn` (`app/schemas.py:225-234`) gains one new optional field, `external_safe: bool = False` (decision 4) — additive and backward-compatible (an existing caller of `POST /v1/doctrine/global` that omits it keeps working, defaulting every rule closed), but it is a real, deliberate deviation from "no schema implications at all" and is called out here explicitly rather than left implicit. Decisions 1, 2, 3, and 5 add no schema of any kind; decision 4 is the sole exception, confined to this one new optional boolean.
- **The doctrine checklist starts empty until the owner re-authors doctrine, and that's an accepted, temporary cost, not a bug.** None of the owner's current 12 rules has `external_safe: true` (the field doesn't exist yet on any of them); the checklist's "sensible default" only materializes once he deliberately resubmits his doctrine with the field set on the rules he judges portable — a normal doctrine version bump this system's supersede-never-erase design already exists to support, not a special migration step. Until then, the feature still behaves safely (nothing preselected, the owner picks by hand every time), which is strictly better than either wrong default (something inapplicable preselected and accidentally copied, or something useful never offered) would have been.
- **The room-setup briefing (decision 2) discloses no fleet data by design — stated explicitly so a future reader doesn't assume the earlier, live-data-driven framing survived.** It is a pure function of `ROOM_MODES` and `app/rooms.py`'s module-level validator constants, computed once at process start, with no database access of any kind. It is safe to paste into literally any external LLM conversation, regardless of what that LLM already knows, because there is nothing fleet-specific in it to know.
- **The doctrine copy (decision 4) is a real, deliberate disclosure the owner is knowingly making — this is the one place that trade-off still applies, though narrowed by this revision to whatever subset he's actually checked.** Each included rule's text leaves Brainard's boundary the moment it's pasted somewhere external; this is not new exposure created by this ADR (the same rule text already renders in full on `/ui/doctrine` today, and the *full, unfiltered* compiled doctrine — non-negotiable and default rules verbatim — already flows to *every* authenticated machine via `GET /v1/bootstrap`'s operating instructions, `app/routers/bootstrap.py`, a much wider audience than "an owner who deliberately checked some boxes and clicked copy"). Decision 4's checklist is, if anything, more conservative than plain clipboard-readiness alone: it also stops the owner from handing an external LLM instructions it cannot act on, which was the actual complaint that reshaped this decision.
- **No token, URL, or credential can appear in any of the three copied blocks, by construction, not by convention.** The room-setup briefing never touches the database at all. The doctrine checklist/copy only ever reads `DoctrineVersion.content`/`.rules`/`.version` (plus the new `external_safe` flag riding along on the same rows) — columns that hold owner-authored doctrine text, never a `Machine.token_hash` or any other credential-bearing column; nothing plumbs a base URL or token into it (unlike `app/onboarding.py`'s join/onboarding prompts, which deliberately *do* carry a base URL and a token placeholder because those prompts are for the owner's *own* fleet — this ADR's briefings are for outside a boundary those prompts never cross, so they omit both entirely, by omission of any call to `resolve_base_url`/`TOKEN_PLACEHOLDER`, not merely by not happening to mention one). The paste-parser (decision 3) only ever reads from the already-rendered page's DOM (the pasted textarea and the existing `ROOM_MODES_JSON` payload) and writes plain strings into ordinary form field `.value` properties — it has no code path that could introduce a credential even if one appeared in a hostile paste.
- **Anti-drift**, restated concretely: decision 2's spec and decision 4's doctrine text are both generated from the same constants/rows the server itself validates against or serves (`ROOM_MODES`, `app/rooms.py`'s bounds, `DoctrineVersion`), never restated as separately hand-maintained numbers — a future change to a bound, a new mode, or a doctrine edit reaches the next copy automatically. The English sentences wrapping those facts remain hand-written and must still be kept honest by whoever changes the underlying rule, the same residual risk every generated-prompt docstring in this codebase already carries (noted, not newly introduced).
- **No interaction with the 32 KB bootstrap budget, stated explicitly so it isn't assumed.** `SIZE_BUDGET_BYTES` (`app/routers/bootstrap.py`) governs one endpoint, `GET /v1/bootstrap` — an entirely separate code path from all three features here. None of the three adds a new endpoint at all: decisions 2 and 4 piggyback on existing owner-only page `GET`s (`/ui/rooms`, `/ui/doctrine`) that already render successfully today, and decision 3 is pure client-side JavaScript with no endpoint whatsoever. `app/routers/bootstrap.py` is neither imported by nor aware of any file this ADR touches.
- **The paste-parser is a new, but tightly bounded, injection surface.** The pasted block is attacker-influenceable if the owner pastes something hostile (a manipulated or compromised external LLM's output) — but the parser only ever writes plain strings into ordinary `<input>`/`<select>` `.value` properties, never into `innerHTML`, never through `eval`/`Function`, and never directly to the server. The worst a hostile paste can do is populate the visible form with attacker-chosen text that the owner must still notice and deliberately submit through `create_room`'s completely unchanged, full validation (length caps, range checks, membership requirements) — the identical trust boundary that already exists for anything the owner types into this form by hand today. A sane client-side max length on the paste textarea is a basic sanity bound, not a security control (nothing downstream ever trusts the pasted text without going through `create_room`'s validators regardless).
- **Every existing render site of `rooms_list.html` needs the new context key(s).** `app/routers/ui_rooms.py` already re-renders this template from three places — the successful `GET` (`rooms_list`), and two `except ApiError` branches (`rooms_create`, `rooms_assign_group`) — and ADR-0018 decision 13 already established that every one of the three must stay in sync when a new template-required context key is added (`active_machines`/`project_names` were threaded through all three then). The same discipline applies here for the room-setup briefing constant, though it is a simpler case: since it is a static, import-time value rather than something fetched per request, it can be imported directly wherever needed rather than re-fetched, which removes one of the three ways ADR-0018's version of this problem could have gone wrong (no `await` to forget).
- **Downstream, to be delivered by this ADR's implementation (not built by this document):** `app/room_setup_briefing.py` (the module-level, import-time-computed format-spec constant); `app/static/room_setup_paste.js` (the structural parser); one new optional field, `external_safe: bool = False`, on `DoctrineRuleIn` (`app/schemas.py`) threaded through `_validate_global_rules`/`_compile_doctrine`/the UI doctrine route; `app/static/doctrine_copy.js` (rebuilds the doctrine copy text from the checklist's current state); template/router changes to `rooms_list.html`, `app/routers/ui_rooms.py`, `doctrine.html`, and `app/routers/ui_doctrine.py` to wire the two new hidden containers, the rule checklist, and the paste box into the existing pages. `app/static/main.js` is imported unchanged (decision 5) and is not part of this list.
