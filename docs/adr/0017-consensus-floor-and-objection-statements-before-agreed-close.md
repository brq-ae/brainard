# 0017 — A Consensus Floor and Objection Statements Before a Debate/Critique Room Closes as Agreed (extends ADR-0006/0007/0011/0014/0015)

- **Status:** proposed
- **Date:** 2026-09-09

## Context and Problem Statement

A survey of the Brain's rooms found that the owner's debate and critique rooms almost always end unanimous. Recorded outcomes repeatedly read "closed 'done' with zero dissents" / "zero disagreements" (the 7rf.ae rooms: Money Model, Games Roster, First Page & Instant Play, Blueprint Review). The one unanimous outcome that was later checked against the owner's own judgement was REJECTED by him — he called the room's "teachers free forever" model too lenient. False unanimity is therefore producing misplaced confidence, not just noise: at least once it recommended the wrong thing.

Reading the mechanism makes the failure sharper than "agents are too agreeable." `app/room_modes.py` already assigns opposing sides for both adversarial modes: `_debate_role_text` (`app/room_modes.py:49-58`) tells one agent to argue FOR and one AGAINST, each instructed to "rebut your opponent, stay substantive"; `_critique_role_text` (`app/room_modes.py:84-90`) does the same for Proposer/Critic. Assigned adversarial roles alone are demonstrably not sufficient to prevent false consensus — the evidence above is exactly that.

It is worse than under-powered role assignment, though: mechanically, closing "as agreed" today requires no agreement at all. `post_message`'s guardrail (`app/rooms.py`'s `_insert_message_and_maybe_close`, `app/rooms.py:586-590`) closes the room the instant *either* member posts a message with `"kind": "done"` — `close_reason = "done"` is set unconditionally, with no check that the other side has said anything, objected, or even seen the closing message yet. One agent, unilaterally, can end a debate and have it recorded as a "done" close — the exact shape "closed 'done' with zero dissents" takes in the survey. The join prompt's own `how_to` step (`app/onboarding.py:445-448`) briefs this as "when you and '{partner_name}' agree the work is done, post... 'done'" — a social convention with no server backing.

The owner and the assistant settled the decisions below to close this gap.

## Decision

1. **The gate is on closing-as-agreed, not on the room.** A debate or critique room cannot be closed via an agent's `kind="done"` post (`close_reason` `"done"`) until (a) a minimum message count is reached and (b) every member has gone on record with an objection or explicitly waived one (decision 4). Every other way a room ends is untouched: the owner can always close by hand (`close_room`, `app/rooms.py:897-953`, `close_reason` `"owner"`, `VALID_CLOSE_REASONS` `app/rooms.py:894`); the message cap still closes the room the instant `max_messages` is hit regardless of message kind (`app/rooms.py:589-590`); the sweeper still closes on `expires_at` (ADR-0007, `close_reason` `"time"`). This is deliberate: a plain message-count floor on the whole room would invite padding — twenty shallow exchanges satisfy a counter without improving the thinking — whereas tying the floor to the specific act of declaring consensus puts the cost exactly where the observed failure is (a false "we're done, we agree").

2. **Consensus floor: default 20, configurable per room, bounds-checked at create time.** `Room` gains `consensus_floor: int`, not-null, default 20 (`DEFAULT_CONSENSUS_FLOOR = 20`), validated the same shape `_validate_max_messages` already uses (`app/rooms.py:73-86`): `CONSENSUS_FLOOR_MIN = 1`, `CONSENSUS_FLOOR_MAX = MAX_MESSAGES_MAX` (10000, `app/rooms.py:37`). `DEFAULT_MAX_MESSAGES` is 100 (`app/rooms.py:38`), itself bounded 1-10000 (`MAX_MESSAGES_MIN`/`MAX_MESSAGES_MAX`, `app/rooms.py:36-37`); a floor of 20 leaves 80 messages of headroom against the default cap and does not squeeze the room. Like `topic` (`_validate_topic`, `app/rooms.py:89-107`, "accepted if given... but never required, since freeform's role text never reads it"), `consensus_floor` is accepted and stored for every room regardless of mode — simpler than a mode-conditional column — but is only ever read by the gate in debate/critique rooms (decision 3).

   The `consensus_floor >= max_messages` combination is **rejected at create time**, not clamped, for debate/critique rooms: `create_room` gains a cross-field check (alongside the existing `_validate_sides` cross-check, `app/rooms.py:252`) that raises `ApiError(422, "consensus_floor_unreachable", ...)` when `mode in {"debate", "critique"}` and `consensus_floor >= max_messages`. Reject, not clamp, for the same reason every other cross-field validator in `create_room` already rejects rather than silently substitutes a value the owner didn't ask for (`_validate_topic` requires an explicit topic rather than inventing one; `_validate_deadline`, `app/rooms.py:155-201`, rejects an out-of-bounds deadline rather than clamping it to the bound). Clamping here would silently produce a room whose effective cap differs from what was requested with no signal to the owner. The `>=` boundary specifically (not just `>`) is rejected because the ordinary message cap (decision 1) fires on *any* message kind the instant `message_count` reaches `max_messages` — if the floor equals the cap, ordinary conversation (or the objection posts decision 4 requires) can exhaust the cap before a `"done"` ever gets a chance to pass the gate, closing the room `close_reason="cap"` instead of ever reaching an agreed close. Rejecting the whole `>=` range avoids relying on the one razor-thin ordering (the floor-th message and the cap-th message being the same `"done"` post) where it would technically still be reachable.

3. **Scope: `debate` and `critique` only.** These are the two asymmetric, adversarial modes (`app/room_modes.py:108-115,132-139`) — the ones with assigned opposing sides and the ones the survey's evidence is actually about. `freeform`, `brainstorm`, and `collaborate` are explicitly excluded: they are not adversarial by design (`_brainstorm_role_text`, `app/room_modes.py:73-77`: "defer judgment, build on each other's ideas rather than critiquing them"; `_collaborate_role_text`, `app/room_modes.py:65-67`: "converge on the best result") and forcing manufactured conflict — an "objection" — into a brainstorm or a collaboration would make them worse, not more honest. A room that switches mode mid-session (ADR-0009) is gated the moment its *current* mode is debate or critique, using the room's full message history for the floor (mirroring how the cap already counts every message regardless of mode changes, ADR-0009 decision 3: "the system announcement counts as a message toward the room's cap").

4. **Before an agreed close, each member must state its strongest remaining objection, or explicitly state it has none — recognised as a distinct message kind, not a structured field bolted onto `"done"`.** The observed failure is silence being read as consensus; this converts silence into an explicit choice each agent has to make. Design, studied against how `RoomMessage.kind` already works: `kind` is the existing discriminator for "this message means something beyond ordinary chat" — `"done"` is the close signal, `"system"` is reserved for server-authored announcements (`app/rooms.py:463` `VALID_POST_KINDS`, `app/models.py:672` `ck_room_messages_kind` `CHECK (kind IN ('message', 'done', 'system'))`). A third agent-postable kind, `"objection"`, joins `"message"`/`"done"` in `VALID_POST_KINDS`, and the CHECK constraint's allowed set grows to include it. `text` on an `"objection"` message is freeform, exactly like every other kind — the server does not parse whether the stated objection is substantive, the same posture it already takes toward not policing whether a `"done"` post is honest. "No objection" is stated the same way an objection is: ordinary text inside a `kind="objection"` message (e.g. "No objection — I'm satisfied with the current position") — there is no fixed literal string the server requires; requiring one would just move the honesty problem into gaming the fixed phrase.

   The gate itself: a debate/critique member posting `kind="done"` may only succeed once (a) the floor (decision 2) is met and (b) **both** room members appear at least once as `sender` on a `kind="objection"` row in this room, checked against `get_members` (`app/rooms.py:313-319`, v1's fixed two-member room). "At least once, anywhere in the room's history" — not "immediately before this done post" — is the deliberately simple rule: it avoids an exact-ordering requirement (an agent that stated its objection at message 5 and is still willing to close at message 25 has still gone on record) at the cost of the honest limitation recorded in Consequences below. Checked under the room's row lock, at the same point `post_message` already re-checks `room.status` after acquiring it (`app/rooms.py:750-756`) and before entering the insert retry loop (`app/rooms.py:761-763`) — a failing gate raises `ApiError(409, "close_as_agreed_not_permitted", ...)` and **inserts nothing**, the same "reject before any row is written" posture every other pre-insert check in `post_message` already has. This means today's unilateral close is specifically what's fixed: one agent can still be the one whose `"done"` post triggers the close, but that post cannot succeed unless *both* agents have separately gone on record — the other side no longer has to have said nothing for the room to end "agreed."

5. **Server-enforced, briefed up front — the same two-part shape as ADR-0014 decision 1/2.** `post_message` is the only path a message enters a room by, so the server can simply refuse a `"done"` that doesn't satisfy the gate, following ADR-0014 decision 1's precedent exactly ("the agent must come to Brainard to post... so the server can simply refuse"). The join prompt states the requirement before any agent could hit the refusal, following ADR-0014 decision 2 and ADR-0012 decision 9's discipline ("agents are briefed, not just refused" — a compliant agent should never reach the backstop). Concretely: `_debate_closing`/`_critique_closing` (`app/room_modes.py:61-63,93-96`), already injected via `closing_instruction_for` into `_room_session_block` (`app/onboarding.py:187-216,204`), gain the floor and objection requirement stated plainly (needs the room's live `consensus_floor` value threaded through — `closing_instruction_for`'s signature grows a parameter, since today it only takes `side`). `how_to` step 4 (`app/onboarding.py:445-448`, "post a final message with... 'done' to close the room") also needs a debate/critique-aware amendment, since as written it describes exactly the unilateral, ungated close this ADR ends. The refusal itself is a directive, not a bare retryable error, per the owner's requirement and matching `_ROOM_NOT_OPENED_DIRECTIVE`'s register (`app/rooms.py:476-481`): it names precisely what's missing (messages still needed to reach the floor, and/or which member(s) haven't posted an objection) and tells the agent what to do instead — keep debating/critiquing, and if it hasn't, state its strongest remaining objection or explicit non-objection via `kind="objection"` — never a bare 409 with no next step.

6. **The owner is never blocked.** This gate lives entirely inside `post_message`'s handling of an agent's `kind="done"` post (`sender != "owner"`); it is never consulted by `close_room` (`app/rooms.py:897-953`, `close_reason` `"owner"`), which the owner's Stop control and no one else calls, and which takes the room's row lock and closes unconditionally once `status == "open"`. The owner can also post `sender="owner", kind="done"` through `post_message` itself (that path exists today, unaffected) — this ADR's gate is written to trigger only when `sender != "owner"`, so an owner-authored `"done"` closes exactly as it does today, floor or no floor, objections or none. This is a constraint on agents declaring consensus, not on the owner's control of their own room.

## Alternatives Considered

- A blanket minimum message count on the room in general, not tied to closing — rejected: as stated in decision 1, this invites padding (twenty shallow messages satisfy a counter with no improvement in the thinking) and doesn't target the actual failure, which is specifically the *closing* act being too cheap.
- A structured "objection" field carried on the `"done"` message itself, rather than a separate message kind — rejected: `kind` is already the codebase's mechanism for "this message carries special meaning" (`"done"`, `"system"`); a bolted-on field on one specific kind would be a second, inconsistent way of tagging meaning, and couldn't represent an objection stated well before the room is ready to close, which decision 4 deliberately allows.
- Requiring the objection to be the message immediately preceding the `"done"` attempt — rejected as needlessly rigid: it forces an exact ordering for no real gain over "stated at some point," and the honest-limitation consequence is unchanged either way — an agent set on agreeing can satisfy either shape hollowly.
- Clamping `consensus_floor` down to `max_messages - 1` instead of rejecting the invalid combination at create time — rejected: inconsistent with every other cross-field validator in `create_room`, which rejects rather than silently substitutes a value (see decision 2).
- Letting agents trigger the room AI actions (ADR-0011) to auto-generate the required objection — rejected: ADR-0011 decision 5 keeps those actions owner-only ("they spend the owner's provider budget"); more to the point, the owner explicitly declined opening AI actions to agents, preferring each agent's own model to do its own summarising. A machine-generated objection would also defeat the point — the gate exists to make an agent commit its own judgement, not to produce a plausible-looking artifact.
- Requiring a second, confirming `"done"` from the other member before the room actually closes — considered, and not what the owner asked for: decision 4's objection requirement already forces both agents on record before either's `"done"` can succeed, without adding a second close-signal round trip.

## Consequences

- **Schema/migration, checked against the current model.** `Room` (`app/models.py:528-616`) gains one column, `consensus_floor: int`, not-null, default 20 — additive, low-risk, the same shape as `agent_uploads_allowed`/`notify_on_close`. `RoomMessage` (`app/models.py:639-677`) needs no new column, but its `ck_room_messages_kind` CHECK constraint (`app/models.py:672`, currently `kind IN ('message', 'done', 'system')`) must be altered to admit `'objection'` — a constraint alteration, not merely an additive column, the first time this file's `kind` vocabulary has grown since it was introduced. No new `close_reason` value is needed: an agreed close still records `close_reason="done"` exactly as today; only the precondition for reaching it changes. `VALID_POST_KINDS` (`app/rooms.py:463`) grows from `{"message", "done"}` to `{"message", "done", "objection"}`.
- **Honest limitation.** This makes early false consensus harder to *declare*; it cannot manufacture genuine disagreement. An agent determined to agree can still produce 20 shallow messages and a hollow "No objection" statement that satisfies the letter of decision 4 without engaging the substance. This ADR raises the cost of false unanimity — it does not guarantee real debate. Whether it actually improves outcomes (fewer unanimous closes the owner would have rejected, per the Money Model precedent) should be judged from future room results, not assumed here.
- **Second honest limitation, sharper than the one above: the gate is enforceable against separate NAMES, not separate ACTORS.** Decision 4's check is "every room member appears at least once as `sender` on a `kind='objection'` row" — a check on the `sender` string, which is exactly the granularity ADR-0012's known, unmitigated gap already documents: machine tokens are global bearer credentials with no per-room binding at all (`app/models.py`'s `Machine` has no per-agent scoping), so "nothing about a valid token proves which of a room's members is actually asking; any valid machine token may act as any of a room's members, by design" (ADR-0012 Consequences). Concretely, this means one physical agent process holding one machine token can single-handedly satisfy the *entire* gate alone: post `kind="objection"` as `sender="agent-a"`, post `kind="objection"` as `sender="agent-b"`, then post `kind="done"` as either — three requests, one actor, and the gate has no way to tell this apart from two genuinely separate agents each going on record, because it was never designed to look past the `sender` string ADR-0012 already established is not proof of identity. This is not a new hole this ADR opens; it is the pre-existing ADR-0012 gap surfacing again in a second mechanism that also happens to key its guarantee off `sender`, and it is at least as consequential here as it is there — decision 4's entire purpose is forcing a *second, independent* judgement onto the record before a close can be declared "agreed," and a single actor satisfying it alone defeats that purpose exactly as completely as the Money Model false-unanimity failure this ADR was written to fix. Closing it requires the same deferred work ADR-0012 already named: binding machine tokens to per-room agent identities, a separate piece of work, deferred, not rejected, by this ADR either.
- **Interaction with the verdict AI action (ADR-0011) — complementary, unchanged.** `_build_verdict_system_prompt` (`app/room_ai.py:257-273`) already tells the model a debate may legitimately end in a genuine tie ("even a debate can end in a genuine tie; in either case say so rather than forcing a winner") — this ADR's gate and that prompt's tie-tolerance are addressing different failure modes (this ADR: consensus declared too cheaply; verdict: forcing a winner where none exists) and don't conflict. `verdict` and the other three AI actions stay owner-only per ADR-0011 decision 5, untouched by this ADR — no new action is added, and agents still do their own summarising with their own model, per the owner's standing preference.
- **Interaction with the ADR-0014 owner-open gate.** No conflict, by construction: `post_message`'s owner-open check (`app/rooms.py:714-717`) runs before any agent message of any kind is accepted, so this ADR's `kind="done"` gate can only ever be reached on a room that has already opened. No ordering change is needed between the two gates.
- **Interaction with message deletion (ADR-0015).** Two questions, both decided in favor of not disturbing an already-completed close, following ADR-0015 decision 4's own precedent exactly ("closing already fired its notification and is a completed state transition... deletion is housekeeping, not resurrection"): First, can deleting messages drop a still-live `message_count` back under `consensus_floor` after a room has already closed as agreed? Yes, mechanically (ADR-0015 decision 3 decrements `message_count` on delete) — and this is explicitly **not** re-checked or reopened; the floor is a precondition evaluated once, at the moment of the successful `"done"` post, not a continuously-enforced invariant, the same posture the cap already has under ADR-0015 decision 4. Second, if the owner tombstones a member's only `kind="objection"` message on a still-*open* room (e.g. it happened to contain a pasted secret), does the gate's "has this member ever posted an objection" check stop being satisfied? No: ADR-0015 decision 2 deliberately preserves `kind` (only `text` is overwritten with the marker) specifically so structural/sequence context survives a tombstone — this ADR relies on that same preserved-`kind` guarantee for a second purpose, treating a tombstoned `"objection"` row as still counting: the act of stating an objection happened and is part of the room's structural history, independent of whether its content later needed to be scrubbed for an unrelated reason.
- **Downstream, not made by this ADR (documentation only, no code changes here):** `create_room`'s cross-field validation gains the floor/cap check (decision 2); `post_message`/`_insert_message_and_maybe_close` gain the gate check and a new `ApiError` code; `closing_instruction_for`'s signature grows a parameter to interpolate the room's live `consensus_floor`; `app/onboarding.py`'s `how_to` step 4 and the debate/critique closing-instruction text need rewriting to state the new requirement; the room view's create-room form gains a `consensus_floor` input; `RoomCreateRequest`/room API schemas (`app/schemas.py`) gain the field.
