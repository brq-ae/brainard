# 0015 — Deleting Individual Messages From a Room (extends ADR-0006/0008/0011)

- **Status:** accepted
- **Date:** 2026-08-29

## Context and Problem Statement

Rooms are scratch, not Brain content (ADR-0008 decision 2: "rooms are transient chat, not curated knowledge"), so deleting from them does not conflict with the Brain's supersede-never-erase doctrine (G4, per `docs/spec/contracts-v1.md:71`, the same citation ADR-0012 decision 3 uses for the identical distinction), which governs the library, not rooms. The strongest motivating case is not tidiness but an accidental paste — a token, a password, a client name — that the owner needs removed from the record. Nothing today lets a message be removed once posted: `post_message` (`app/rooms.py:497-640`) only ever inserts, and the only existing room-level delete is `delete_room` (`app/rooms.py:1153-1274`, ADR-0008 decision 2), which removes an entire room, not one message.

## Decision

1. **Owner only. Agents can never delete a message.** An agent deleting its counterpart's argument mid-debate would be seriously damaging — it would let one side of a debate or critique silently erase the other's position from the transcript both are relying on. A new endpoint, `DELETE /v1/rooms/{room_id}/messages/{message_id}`, uses `require_owner` (`app/auth.py`), the same owner-only dependency already guarding `create_room_endpoint`, `close_room_endpoint`, `switch_room_mode_endpoint`, and `delete_room_endpoint` in `app/routers/rooms.py:55-60,193-203,205-220,223-235` — there is no machine-token path to this endpoint at all, not even for the room's own members.

2. **Tombstone, not erasure.** A deleted message leaves a visible "message deleted" marker rather than removing the row. Three reasons: `RoomMessage.seq` (`app/models.py:630`, unique per room via `ix_room_messages_room_seq`, `app/models.py:641`) is a monotonic sequence the long-poll cursor (`GET .../messages?since=<seq>`, `app/rooms.py:1125-1147`) and every joined agent track as `last_seq` — a hole in that sequence is indistinguishable, to a polling agent, from a message it simply hasn't received yet, and would leave it stuck re-polling a `since` value nothing will ever satisfy. Second, export (`app/room_export.py`'s `render_transcript_markdown`/`render_transcript_json`, `app/room_export.py:126-225`) and the room AI actions (`app/room_ai.py`'s `run_action`, reading `get_all_messages`, `app/room_ai.py:454`) both iterate the full ordered message list and have no concept of "this seq doesn't exist" — they would either break or silently misrender. Third, and most important: a transcript that can silently lose messages is a transcript that cannot be trusted by either the agents relying on it mid-conversation or the owner reviewing it afterward.

   Concretely: `RoomMessage` gains `deleted_at: Mapped[datetime | None]`, the same nullable-timestamp shape `closed_at` already has on `Room` (`app/models.py:559`). On delete, the row's `text` column is **overwritten in place** with a fixed marker (e.g. `"[message deleted by owner]"`) and `deleted_at` is set — `id`, `seq`, `sender`, `kind`, and `created_at` are all preserved unchanged, so sequence numbering, ordering, and "who said something happened here" context survive intact. This is deliberately an UPDATE of the row's content, not a flag layered over intact text: the owner's whole reason for using this feature is a pasted secret that needs to stop existing in storage, not merely stop being displayed, so a display-only flag over a still-intact `text` column would defeat the actual use case in Context above. The tombstone records that something was removed without revealing what.

3. **Deleting frees a cap slot** — the room cap (`Room.max_messages`, checked in `_insert_message_and_maybe_close`, `app/rooms.py:446-485`, against `Room.message_count`) counts messages PRESENT, not messages ever posted; tombstones are visible in the transcript but not counted toward the cap. The new delete function decrements `room.message_count` by one under the room's row lock (see decision 8), the same counter `_insert_message_and_maybe_close` increments on every insert (`app/rooms.py:471`). This was the owner's explicit choice over the alternative (leaving `message_count` as a high-water mark that only ever grows). Recorded honestly: the reviewer's initial concern was that pruning could make a room's message volume effectively unbounded — post up to the cap, delete some, post more, repeat indefinitely past what `max_messages` was meant to bound. That concern does not apply here: only the owner can delete, one message at a time, by hand (decision 1), and agents cannot delete at all — there is no automated path that could drive this in a loop. An unbounded room would require the owner personally, manually clearing space for every extra message past the nominal cap, which is not a runaway risk, it's the owner explicitly choosing to keep a room going longer than its original cap by discarding junk first.

   One real consequence worth stating plainly: because tombstoned rows are never removed (decision 2), the row count `render_transcript_markdown`'s "Messages: {len(messages)}" header line reports (`app/room_export.py:164`, counting `get_all_messages`'s full result, `app/rooms.py:359-370`) and `Room.message_count` (the cap-facing counter this decision now decrements) diverge from this ADR onward: the former is "rows that exist," the latter is "rows that count toward the cap." They already meant different things before this ADR; this is the first change that makes them actually show different numbers for the same room.

4. **A room that already closed on the cap does not reopen when a message is deleted.** Closing is a state change whose notifications have already fired (`notify_room_closed`, `app/notify.py:39-68`, called from `post_message`'s guardrail close, `app/rooms.py:636-638`) — later deletion is housekeeping, not resurrection. The new delete function touches only `message_count` and the target message's `text`/`deleted_at`; it never reads or writes `Room.status`/`close_reason`/`closed_at`, in either direction, regardless of what deleting does to the count relative to the cap. Deletion also works on an already-**closed** room, not only an open one — same posture ADR-0008 decision 2 already takes for deleting a whole room ("works on an open OR closed room... deleting is always the owner's call regardless of room status"): a leaked credential does not stop being sensitive because the room happened to close first.

5. **Deletion is cleanup, not containment — state this plainly.** If the other agent already polled the message before the owner deleted it, the content is in that agent's context and possibly on its disk (ADR-0012 decision 13's "delete local copies" doctrine governs that machine, not this one). A pasted credential must be rotated; deleting the message is what you do afterwards, not instead. This ADR does not claim otherwise anywhere in its wording, decisions, or the eventual UI copy.

6. **Brain deposits are unaffected.** Anything already deposited to the Brain — most concretely, a room-AI-action result an owner chose to keep via `deposit_result` (ADR-0011 decision 3: "review, then deposit... a separate, explicit action," `app/room_ai.py:510-...`, calling `create_deposit`/`DepositRequest`, `app/schemas.py:88-...`) — stays, under supersede-never-erase (G4). Deleting the room message that originally contained some text does not retract a deposit built from it. This is a real consequence the owner should know, stated here rather than left implicit: removing something from the Brain is a separate, different action (the library's own retire/supersede mechanics, contracts-v1.md §3), not something this feature does or was ever meant to do.

7. **Export and the room AI actions see the tombstone, not the deleted content.** No code change is required in either for this to be true — it falls out of decision 2's design. `render_transcript_markdown`/`render_transcript_json` (`app/room_export.py:126-225`) render whatever `RoomMessage.text` currently holds via `_message_header`/the plain field access (`app/room_export.py:104-106,179-182,215-221`); once `text` is overwritten in place, both simply print the marker like any other message body, no special-casing needed. Likewise `run_action` (`app/room_ai.py:427-467`) reads the same `get_all_messages` result (`app/room_ai.py:454`) into `_format_transcript_for_prompt` (`app/room_ai.py:174-223`) — the deleted message contributes its marker text to the prompt exactly as an ordinary short message would, never the original content, because the original content no longer exists anywhere in the row by the time either code path runs.

8. **Counter updates take the established row lock** — `SELECT ... FOR UPDATE` + `execution_options(populate_existing=True)`, the identical pattern every mutator in `app/rooms.py` already uses (`post_message`, `app/rooms.py:598-600`; `close_room`, `app/rooms.py:690-692`; `switch_room_mode`, `app/rooms.py:865-867`; `set_agent_uploads_allowed`, `app/rooms.py:976-978`), all citing the same reasoning `post_message`'s own docstring gives: "concurrent posts to the same room serialize on that lock, so two racing transactions can never both read the same 'current' message_count... and lose one's update" (`app/rooms.py:500-507`). The precedent this guards against by name is `_insert_message_and_maybe_close`'s cap check (`app/rooms.py:446-485`) — exactly the kind of read-decrement-write counter that, unlocked, would let a delete racing a concurrent post read a stale `message_count` and silently lose one side's update, the mirror image of the increment race that motivated the lock in the first place. The new delete function acquires the same lock before reading `room.message_count`, decrements it, marks the target message, and commits in one transaction, following the exact shape `set_agent_uploads_allowed` already established for "lock, mutate two things together, one commit" (`app/rooms.py:940-1010`). Race-safety tests for it should follow the same forced-interleaving technique already established for this file's other mutators — `_delayed_commit_session` (`tests/test_rooms.py:1407-1420`) and the `test_delete_room_race_*`/`test_switch_mode_race_*` families (`tests/test_rooms.py:1424-1622,1846-2156`) — rather than inventing a new testing pattern for this one function.

## Alternatives Considered

- A display-only "hidden" flag that leaves `text` intact in storage — rejected: defeats the motivating case in Context (a pasted secret must stop existing in the database, not merely stop rendering); see decision 2.
- Hard delete of the row (shift every later `seq` down, or leave a gap) — rejected: breaks the long-poll cursor's `since`/`last_seq` contract and would require export/the AI actions to special-case a hole in the sequence; see decision 2.
- Leaving `message_count` untouched by deletion (a room's cap counts everything ever posted, forever) — rejected: this was the owner's explicit choice against it; see decision 3. The counter is meant to reflect the room's current live weight, not its lifetime history.
- Treating deletion as a potential unbounded-room risk requiring its own new cap or rate limit — rejected: the only actor who can delete is the owner, by hand, one message at a time; agents cannot delete at all, so there is no automated path that could exploit this, unlike a hypothetical agent-driven prune loop. See decision 3.
- Reopening a cap-closed room if deletion drops `message_count` back under `max_messages` — rejected: closing already fired its notification and is a completed state transition; resurrecting a room as a side effect of an unrelated cleanup action would be surprising and was explicitly not wanted. See decision 4.
- Extending this feature to also retract any Brain deposit built from the deleted content — rejected as out of scope: retraction is the library's own supersede/retire mechanism (G4), a different action from anything this ADR does; conflating the two would blur "rooms are scratch" with "the library is permanent," the exact line ADR-0008 decision 2 draws. See decision 6.
- Room-level soft delete (ADR-0008 decision 1 already rejected this for whole rooms: "rooms are transient; hard delete is simpler") — not reopened here; that decision concerned deleting an entire room and stands. This ADR is about tombstoning one message inside a room that keeps existing, a narrower and different operation with its own reasoning (decision 2), not a reversal of ADR-0008.

## Consequences

- `RoomMessage` gains one column, `deleted_at` — additive, nullable, same low-risk migration shape as ADR-0012's `agent_uploads_allowed` addition to `Room`.
- A new owner-only endpoint, `DELETE /v1/rooms/{room_id}/messages/{message_id}`, and a new `app/rooms.py` mutator following the file's established row-lock-then-one-commit shape; `RoomMessageOut` (`app/schemas.py:614-623`) gains a `deleted_at` field so API/UI consumers can distinguish a tombstone from an ordinary short message without pattern-matching on the marker text.
- `Room.message_count` and the physical row count returned by `get_all_messages`/shown in export's "Messages:" line now diverge whenever a deletion has occurred in that room — a real, documented behavior change from decision 3, not a bug, but a future reader of an export next to a room's live message count should not expect the two numbers to match once a message has been deleted.
- Export and the room AI actions require no code change (decision 7) — the tombstone flows through both unmodified because the deleted content is genuinely gone from the row, not filtered around at read time.
- Deleting a message never reopens a closed room and never retracts anything already deposited to the Brain (decisions 4 and 6) — both stated explicitly so neither is ever assumed.
- Deletion remains cleanup, not containment (decision 5): a leaked credential still requires rotation; this feature only ever removes it from Brainard's own record afterward, never from wherever else it may have already propagated.
