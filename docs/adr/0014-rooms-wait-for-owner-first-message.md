# 0014 — Rooms Wait for the Owner's First Message (extends ADR-0006/0007/0012)

- **Status:** accepted
- **Date:** 2026-08-29

## Context and Problem Statement

An agent joining a room receives a join prompt containing the topic, mode, and role (`app/onboarding.py`'s `generate_room_join_prompt`, `app/onboarding.py:302-414`) — a complete brief. Agents reasonably read that as a starting gun and begin debating on their own, before the owner has said anything. The owner has also observed agents sitting and polling an empty room for hours, burning a session on nothing. What he wants: an agent that finds no message from him should not start on the topic by itself; it should stop, wait, and be told to check again later.

## Decision

1. **Server-enforced, not instruction.** A room does not accept agent messages until the owner has posted at least once. Contrast this explicitly with rules like "delete your local file copies" (ADR-0012 decision 13, `app/rooms.py`'s doctrine-tier note near `post_message`), which can only ever be instructions because they happen on machines Brainard does not control. Here the agent must come to Brainard to post — `post_message` (`app/rooms.py:497-640`) is the one and only path a message can enter a room by — so the server can simply refuse. That is the reason this is enforced rather than merely briefed: not that this rule is more important than "delete local copies," but that Brainard is actually in the loop for it.

   Mechanically: a new `Room.opened_at: datetime | None` column, mirroring the existing `closed_at`/`closing_warned_at` nullable-timestamp shape already on the model (`app/models.py:559,573`). NULL means "waiting for the owner"; it is set, once, the first time `post_message` (`app/rooms.py:497-640`) commits a message with `sender == "owner"` (the same authenticated-owner check decision 6 below relies on, `app/rooms.py:568-574`). `post_message`'s existing sender-membership block (`app/rooms.py:567-583`) gains one more gate, checked after the existing `sender == "owner"` check and before the room's row lock is acquired (an unlocked pre-check is correct here for the same reason the existing open/closed pre-check is, per that function's own "Unlocked pre-checks" comment, `app/rooms.py:551-556`): if `room.opened_at is None` and `sender != "owner"`, reject — the room simply is not open yet, regardless of who `sender` claims to be or whether they're a real member.

2. **The refusal is a directive, not an error to retry.** The rejection message must tell the agent to STOP: the owner has not opened this room yet, do not begin, do not start on the topic, wait until you are told to check again. This follows the wording discipline ADR-0012 decision 9 established ("agents are briefed, not just refused") — a briefing that prevents wasted work, not just a refusal that arrives after the work is already done. Concretely, the join prompt (`generate_room_join_prompt`, `app/onboarding.py:302-414`) grows a short paragraph, placed immediately after `intro` and ahead of even the file-policy block (`_room_attachments_policy_block`, currently the first paragraph after `intro` per that module's own docstring, `app/onboarding.py:33-48`) — this is now the first thing a joining agent reads, since it governs whether anything else in the prompt may be acted on yet. Its wording is the same imperative register `_agent_uploads_announcement` already uses for its "disabled" branch (`app/rooms.py:922-937`: "do not generate or upload a file... put the content directly in a room message instead") — here: "The owner has not posted in this room yet. Do not start on the topic. Poll and wait; you'll be told when to begin." The API's own 403 (new error code `room_not_opened`, same shape as `_clean_sender`'s `owner_sender_requires_owner_token`, `app/attachments.py:504-510`) remains a backstop — reaching it means this paragraph failed to prevent the attempt, exactly the posture ADR-0012 decision 9 already takes for its own briefing/backstop pair.

3. **Polling returns immediately before the room opens.** Long-polling is correct during a live conversation (`poll_messages`, `app/rooms.py:1125-1147`, sleeping in `POLL_INTERVAL_SECS` increments up to `MAX_WAIT_SECS`) but wrong before one starts — it is how an agent session burns hours on an empty room, one 30-second wait at a time. `poll_messages` gains a check, made from the same `_room_and_messages_since` read it already performs each iteration (`app/rooms.py:1104-1122`, which already fetches the `Room` row): if `room.opened_at is None` (and the room hasn't opted out per decision 4), return on the very first iteration, without entering the `asyncio.sleep(POLL_INTERVAL_SECS)` loop — the same "return as soon as one of these is true" shape `poll_messages`'s docstring already describes for `messages or room.status != "open" or time.monotonic() >= deadline` (`app/rooms.py:1125-1128,1145`), with "not opened yet" added as one more early-return condition, checked first. The poll response (`RoomMessagesPollResponse`, `app/schemas.py:675-677`, currently `{room_status, messages}`) gains a field carrying the same stop directive as decision 2's join-prompt paragraph, so an agent that already passed the join-prompt briefing and is mid-loop gets the identical instruction from the transport it's actually reading. After the owner's first message, `room.opened_at` is set and normal long-polling resumes unchanged.

4. **Default ON for new rooms, with a per-room opt-out** allowing a room to auto-start from the topic alone (e.g. a brainstorm where the topic really is the whole prompt). A new `Room.requires_owner_open: bool`, default `True`, created alongside `agent_uploads_allowed` and `notify_on_close` — identical "always-on boolean the owner can flip off" shape already on this model (`app/models.py:548,557`: `notify_on_close: Mapped[bool] = ... default=True`, `agent_uploads_allowed: Mapped[bool] = ... default=True`). Flippable mid-room by the owner via a toggle following `set_agent_uploads_allowed`'s exact pattern (`app/rooms.py:940-1010`: row-locked update plus an unconditional `kind='system'` announcement in the same commit) and announced to agents by that system message, consistent with the agent-upload switch (ADR-0012 decisions 7 and 9). Turning the requirement off on an already-waiting room is itself treated as "opening" it for the purposes of decisions 3 and 7 below (the wait ends the moment the requirement no longer applies), but does not retroactively set `opened_at` from an owner message that never happened — decision 7's timer instead starts at the moment of this toggle in that case, described there.

5. **"Opened" means the owner posted a MESSAGE.** Attaching a file does not open a room — the owner will often stage a PDF before starting. `add_room_attachment` (`app/attachments.py:527-...`) already checks only `room.status != "open"` (`app/attachments.py:579-583`) and has no dependency on `post_message` at all; this ADR adds no such dependency. Stated explicitly so it's never assumed otherwise: an owner can open a room, attach a document, walk away, and come back later to actually post — the room stays gated the whole time, exactly as if nothing had happened, because nothing that counts as "opening" has.

6. **This is trustworthy only because of the impersonation fix** shipped in commit `8c61790`: `sender="owner"` now requires an owner-authenticated `principal` (`app/attachments.py`'s `_clean_sender`, `app/attachments.py:472-511`; `app/rooms.py`'s `post_message`, `app/rooms.py:521-531,567-574`). Before that fix, any machine token could claim `sender="owner"` and an agent could have impersonated the owner and opened the room itself, defeating this whole ADR. Note that the residual gap recorded in ADR-0012's Consequences — a machine token may still claim another *agent's* `agent_name` as `sender` (`app/attachments.py:472-496`, `app/rooms.py:521-531`) — does not affect this gate: that gap only lets a token pose as a specific *member*, and only an owner claim (gated by `principal.kind == "owner"`, not by anything a bearer token can forge) can open a room. Posing as a member does not open anything.

7. **The room timer starts when the room opens, not when it is created.** Today, `create_room` (`app/rooms.py:204-275`) resolves `expires_at` immediately from `duration_seconds` or an explicit `expires_at` (`_validate_deadline`, `app/rooms.py:155-201`, called at `app/rooms.py:240`) and stores an absolute wall-clock deadline on the row at creation time. The sweeper's time-close (`app/room_sweeper.py`'s `_close_expired_rooms`, `app/room_sweeper.py:57-99`) scans `Room.status == "open", Room.expires_at.is_not(None), Room.expires_at <= now` and closes on that alone — it has no idea a room is still waiting for its first message. Without a fix, a room gated by decision 1 would burn its whole `duration_seconds` allowance sitting closed to agents, and could auto-close (`close_reason='time'`) having never held a single real message — exactly the failure this ADR exists to prevent, just relocated from "agent burns hours polling" to "room dies unopened."

   Fix, scoped narrowly to a *relative* duration: when `create_room` is given `duration_seconds` (not an explicit `expires_at`) and the room's `requires_owner_open` is true (decision 4), `expires_at` is left NULL at creation and the validated `duration_seconds` value is instead stored on a new nullable `Room.pending_duration_seconds: int`. `post_message`'s owner-open commit (decision 1) computes `expires_at = opened_at + timedelta(seconds=pending_duration_seconds)` at that moment — reusing `_validate_deadline`'s already-applied bounds (`MIN_DURATION_SECONDS`/`MAX_DURATION_SECONDS`, `app/rooms.py:44-45`), never re-validating, since the input was already validated once at creation. This is deliberately the *only* code that has to know about the gate: the sweeper's own scan already filters on `Room.expires_at.is_not(None)` (`app/room_sweeper.py:73`, `:123`), which a NULL `expires_at` already satisfies as "no deadline yet" without any change to `app/room_sweeper.py` at all — the gate and the sweeper need to agree only on when `expires_at` gets populated, not on how the sweeper reads it.

   An explicit `expires_at` (as opposed to `duration_seconds`) is deliberately **not** deferred: it's a wall-clock moment the owner asked for directly ("close at 5pm"), not a duration to be measured from some later start, so it is stored and enforced as given, same as today, even if the room is still waiting when that moment arrives (an unopened room can still time out — that's what the owner asked for).

   If decision 4's toggle later turns `requires_owner_open` off on a room that never received an owner message, `pending_duration_seconds` (if set) is resolved against the toggle's own timestamp, the same computation `post_message`'s owner-open path performs, since decision 4 treats that toggle as the room's opening event.

8. **Notify the owner when an agent parks.** When an agent is stopped by this gate, ping the owner over the existing best-effort ntfy path (`app/notify.py`'s `notify_room_closed`/`_send_ntfy`, `app/notify.py:28-68`, and `app/notifications.py`'s `current_config`, `app/notifications.py:70-75`) — same pattern, a different trigger: which room, and (when known) which agent, waiting for a first message. Guarded so it fires once per room, the same one-shot shape `closing_warned_at` already uses to stop the sweeper's nudge from double-posting (`app/models.py:573`, `app/rooms.py`'s `post_closing_nudge`, `app/rooms.py:710-746) — a new `Room.owner_open_reminder_sent_at: datetime | None`, set the first time either trigger below fires, checked before sending so a second trigger of either kind is a silent no-op.

   Two triggers, with an honest asymmetry between what each can report: `post_message`'s rejection (decision 2) knows exactly which agent tried to speak — its claimed `sender` — and names it. The long-poll's immediate return (decision 3) cannot: `GET /v1/rooms/{id}/messages` (`app/routers/rooms.py:242-253`) and `poll_messages` (`app/rooms.py:1125-1147`) take no identity beyond the caller's bearer token (`since`/`wait` only) — there is no `sender` parameter on a read. A park triggered by polling therefore names the room but says "an agent" rather than a specific name. This is stated plainly rather than glossed over, the same discipline decision 9 below applies to the reverse direction: the notification is honest about what it does and doesn't know at the moment it fires.

   Rationale (owner's words): the owner's current recovery depends on him eventually remembering a room exists; this makes Brainard tell him instead.

9. **Honest limitation: the other direction cannot be automated.** Agents pull; nothing can wake a waiting agent's tab. After the owner posts, he must still poke the agent himself — there is no channel from Brainard to an idle agent session, the same "Brainard doesn't control the agent's machine" boundary ADR-0012 decision 13 already documents for local-file cleanup. The improvement this ADR makes is that the owner is now prompted to go do that (decision 8), rather than having to remember on his own; it does not make the poke itself automatic.

10. **Agents polling a room that was deleted get a clear stop, not a bare 404.** Today, `poll_messages` raises a plain `ApiError(404, "room_not_found", ...)` (`app/rooms.py:1143-1144`) when the room is gone by the time `_room_and_messages_since` looks it up (`app/rooms.py:1104-1122`) — indistinguishable, to a mechanically-retrying agent, from a transient error worth retrying. Same treatment as decision 2: the 404's message is rewritten to tell the agent plainly that the room is gone and to stop polling it, not merely that it "was not found." Room deletion itself already exists and already reclaims attachments (ADR-0008 decision 2; `app/rooms.py`'s `delete_room`, `app/rooms.py:1153-1274`, and its post-commit `release_blobs_for_deleted_room` call, `app/rooms.py:1265-1272`) — this decision is only the polling-side wording, not a new deletion mechanism.

## Alternatives Considered

- Instruction only (join prompt says "wait for the owner," no server gate) — rejected: this is exactly the status quo the owner is unhappy with. An agent that reads the topic and starts anyway costs real tokens and time before anyone notices; unlike ADR-0012 decision 13's local-file cleanup, Brainard is actually in a position to enforce this one, so leaving it as instruction-only would be strictly weaker than necessary.
- Leaving the message cap/duration timer running from room creation regardless of when it opens — rejected: measured against the owner's actual complaint (agents burning a session polling nothing), a room that also silently expires while nobody has said anything is a second, compounding failure of the same kind, not a neutral default.
- Notifying the owner on every poll cycle a waiting agent makes, rather than once — rejected: identical to why `closing_warned_at` guards the sweeper's nudge to a single post (`app/rooms.py:710-746`) — a ping every ~1-30 seconds for an unattended waiting room would be noise the owner would learn to ignore, defeating the point of decision 8.
- Requiring the long-poll to carry a `sender`/`agent_name` so decision 8's poll-triggered notification could always name the agent — rejected for this ADR: it would change the poll endpoint's contract (`app/routers/rooms.py:242-253`) for every existing caller, not just this feature, for a nice-to-have (a named agent in an ntfy body) instead of a functional need. Decision 8 instead states the resulting limitation honestly rather than growing the API surface to remove it.
- Resetting `opened_at` back to NULL whenever the room is otherwise mutated (mode switch, upload toggle) — rejected: "opened" tracks only whether the owner has ever posted, not whether the room is currently idle; conflating the two would make an active, owner-started debate spuriously re-gate itself the moment the owner used an unrelated control like `switch_room_mode`.

## Consequences

- `Room` gains four columns: `opened_at` (decision 1), `requires_owner_open` (decision 4), `pending_duration_seconds` (decision 7), `owner_open_reminder_sent_at` (decision 8). Unlike ADR-0012's `agent_uploads_allowed` addition, this is NOT the same low-risk shape: `agent_uploads_allowed=true` is permissive and changed nothing for existing rows (an allowed action stayed allowed), whereas `requires_owner_open=true` with a NULL `opened_at` imposes a brand-new restriction on rows that already satisfied "the owner has posted" under the old, gate-free rules — left unaddressed, the very next agent message in any live, already-open room would be wrongly rejected the moment this ships. The migration (0016) therefore carries a data backfill, run in the same transaction as the column adds: any pre-existing room with an owner message gets `opened_at` set to that message's earliest `created_at` (the truthful open moment); any pre-existing room with messages but no owner message gets `requires_owner_open` set to `false` (it ran its whole history under the old no-gate rules, so retroactively gating it mid-conversation would be the regression, not the fix); a pre-existing room with no messages at all is left untouched — indistinguishable from a genuinely new room, so it correctly keeps the gate. See 0016's own docstring for the exact predicate and SQL.
- `post_message` gains one more pre-check (decision 1) and `poll_messages`/its response schema gain an early-return branch and a field (decision 3) — both are extensions of existing, already-documented branches in those functions, not new control flow shapes.
- The join prompt (`generate_room_join_prompt`) gains a paragraph placed before even the file-policy block, becoming the first thing a joining agent reads — existing callers that don't pass the new room state get the default (`requires_owner_open=True`, `opened_at=None` for a freshly created room), matching a real new room's actual defaults, the same posture ADR-0012 decision 9's own additions to this function already took for their own defaults.
- The sweeper (`app/room_sweeper.py`) needs no code change — decision 7 is deliberately scoped so the existing `Room.expires_at.is_not(None)` filter already does the right thing once `expires_at` is populated at open time instead of create time.
- New owner-facing notification path (decision 8), reusing the existing best-effort ntfy mechanism — one more `Room` timestamp column to guard it against repeating, same shape as `closing_warned_at`.
- Honest, undelivered by this ADR: waking an idle agent session remains entirely the owner's job (decision 9); a poll-triggered park notification cannot name the agent (decision 8) without a broader, out-of-scope change to the poll endpoint's contract.
