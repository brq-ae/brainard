# 0013 — Room Page Layout and Join-Prompt Copy Buttons

- **Status:** accepted
- **Date:** 2026-08-24

## Context and Problem Statement

Copying a join prompt currently requires scrolling to the bottom of the room page, expanding the collapsible "Join prompts" `<details>` section (`app/templates/room_view.html:176-185`), scrolling, copying, pasting, then repeating per agent. This is the owner's most repeated manual action on the room page.

## Decision

1. **Section order on the room page**, top to bottom: (a) room info, unchanged; (b) join-prompt copy buttons; (c) export; (d) AI actions; (e) switch mode; (f) transcript; (g) the full join-prompts section, still collapsible, retained at the bottom for when the text itself needs reading. Today's order in `room_view.html` is transcript, export, AI actions, post/stop/switch-mode panels, then the collapsible join prompts at the very bottom (`room_view.html:41-185`) — the new copy-button row is the only new section; everything else is reordered, not rebuilt.

2. **One copy button per participant, generated dynamically** — not hardcoded to two. Rooms iterate `members` already (`room_view.html:10,179`: `{% for m in members %}`), so the new row uses the same loop, not a fixed pair — consistent with rooms supporting free-form groups (ADR-0008 decision 3).

3. **Button labels use the participant's role or side where the room has them** (e.g. "Copy join prompt — Commander"), falling back to "Agent 1 / Agent 2 / …" when it does not. The room already computes each member's side for display (`sides.get(m)` / `side_labels[sides[m]]`, `room_view.html:10`); the new buttons read the same `sides`/`side_labels` context, no new data plumbing. Rationale: the owner is pasting into a specific agent's tab and needs to know which.

4. **Reuse the existing clipboard fallback shape, revised by decision 5 below.** The modern `navigator.clipboard.writeText` API requires a secure context (HTTPS or localhost); the owner reaches this over LAN by plain-HTTP IP, which is neither, so that API is unavailable there — not as a rare edge case, but as this deployment's permanent condition: for as long as the owner reaches the app this way, `navigator.clipboard` is never available, on every page, every click. The existing "Copy transcript" (`room_view.html:65`) and "Copy prompt for {{ m }}" (`room_view.html:182`) buttons already solve the general problem via one generic, already-shared handler in `app/static/main.js:19-40`: a delegated `click` listener on `[data-copy-target]` reads the target element's `.textContent`, and — feature-detecting `navigator.clipboard && navigator.clipboard.writeText` (`main.js:33`) — either writes to the clipboard, or, when that API is absent, falls back to `window.prompt("Copy the token manually:", text)` (`main.js:35,38`), a manual-copy dialog. Naive code that calls `navigator.clipboard.writeText` directly, without this feature-detection and fallback, would throw uncaught in the click handler on this owner's setup — no visible error, the button appears to do nothing, and the owner would go on to paste stale clipboard contents into an agent's tab. That silent-failure mode is exactly why `main.js`'s existing branch exists, and exactly why the new per-participant buttons must reuse it via the same `data-copy-target` markup pattern (a hidden `token-reveal` element with the source text as `.textContent`, `room_view.html:64,181`) rather than writing a second copy-to-clipboard path. What that shared handler falls back *to* is revised below (decision 5) — the `window.prompt` dialog, on its own, still demands manual select-and-copy, which undercuts the one-click goal of this whole ADR.

5. **Three-tier clipboard copy: insert a middle tier between the modern API and the manual-copy dialog.** Because the `window.prompt` fallback fires unconditionally on this deployment (decision 4) and still requires the owner to select and copy the text by hand, leaving it as the only fallback would make the new one-click buttons no better, on this deployment, than the collapsible section they're replacing. Decision: `main.js`'s shared `[data-copy-target]` handler gains a middle tier — write the target text into a hidden `<textarea>`, select it, and call `document.execCommand('copy')`. This API is formally deprecated but still functions in non-secure contexts in every current browser, unlike `navigator.clipboard`. Revised fallback order: modern `navigator.clipboard.writeText` where available (secure contexts) → hidden-textarea `document.execCommand('copy')` → `window.prompt` only as a last resort, for the rare browser where even `execCommand` is unavailable. Because "Copy transcript," "Copy prompt for {{ m }}," the new per-participant buttons, and the export copy button (ADR-0011 decision 1) all share this one handler (decision 4), all of them gain real one-click copying on this deployment as a result — the export button included, at no extra cost, since it was already going through the same code path.

6. **Buttons confirm visually** — flip to a "Copied" state briefly, the same mechanism the existing handler already performs for every `[data-copy-target]` button today (`main.js:26-32`: swaps `btn.textContent` to "Copied!" and restores the original after 1500ms). The new buttons get this for free from the shared handler; no new confirmation logic is written. Rationale: without confirmation, a silent clipboard failure is indistinguishable from success, and the owner would paste stale clipboard contents into an agent.

7. **Transcript becomes collapsible, defaulting to open** (it is the main content — currently the first panel, `room_view.html:41-52`), with a live message count in its header (e.g. "Transcript (23 messages)") so a collapsed room still visibly shows activity while polling. The room already tracks a live count element (`<span id="room-count">{{ room.message_count }}</span>`, `room_view.html:12`, kept current by the short-poll loop's `data.message_count` handling in `app/static/rooms.js:151-153`) — the new transcript-header count reuses that same element/update path, it does not add a second counter that could drift from it.

## Alternatives Considered

- A textarea + `document.execCommand('copy')` fallback — when this ADR was first written, this was not what the codebase did (confirmed by reading `app/static/main.js`), and the ADR preferred accurately citing the real, already-shipped `window.prompt` fallback over describing a mechanism that didn't exist. That reasoning is superseded: decision 5 above now adds exactly this mechanism, as a middle tier, because the plain `window.prompt` fallback turned out to fire unconditionally on this deployment and undercuts the one-click goal these buttons exist for. This entry is kept, corrected, rather than silently dropped, so the reversal is visible.
- Leaving the two-tier `navigator.clipboard`/`window.prompt` fallback as the only option for the new buttons — rejected: `window.prompt` still demands manual select-and-copy by hand, and on this deployment it is the tier that always fires, so it would defeat the purpose of one-click copy buttons rather than deliver it.
- A second, purpose-built copy handler for the new buttons — rejected: `main.js`'s existing `[data-copy-target]` delegated listener is already generic (keyed off a data attribute, not an id), so the new buttons need only the same markup, no new JS.
- A separate message counter for the transcript header — rejected: reuses the existing `#room-count` element/update path so the two displays of the same number can't drift apart.
- Hardcoding two copy buttons (Commander/Builder) — rejected in favor of iterating `members`, since rooms are not limited to two named roles (ADR-0008's free-form groups).

## Consequences

- Presentation-only: one template (`app/templates/room_view.html`) plus reordering — no schema change, no migration, no API change. `app/static/main.js`'s shared copy handler is **not** reused as-is: decision 5 adds a middle clipboard tier (hidden textarea + `document.execCommand('copy')`) inside it, a small, self-contained JS change with no server-side counterpart. `app/static/rooms.js`'s live count update is unaffected and is reused as-is.
- The export copy button (ADR-0011 decision 1) gains real one-click copying on this deployment as a side effect, since it already shares `main.js`'s handler with the new buttons (decision 4) — no separate change needed for it.
- The room page's visual order changes (join-prompt buttons move near the top; transcript moves down and becomes collapsible), which existing screenshots/docs referencing "top of page" layout would need to catch up with.
- The bottom "Join prompts" section is retained, not removed, so nothing that already links to or scrolls to it breaks.
