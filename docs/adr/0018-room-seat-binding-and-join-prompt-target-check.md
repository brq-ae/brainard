# 0018 — Room Seat Assignment/Binding and a Join-Prompt Target Check (extends ADR-0006/0008/0012/0014/0017)

- **Status:** accepted
- **Date:** 2026-09-10 (revised 2026-09-10, before implementation, per owner review)

## Context and Problem Statement

A real incident: the owner pasted a room join prompt into the wrong agent tab — an agent working on an entirely different project. In his words: "this is extremely critical because it cross contaminates other agents and undoing something like this is a huge headache." The wrong agent immediately has another project's brief sitting in its context and may act on it.

This is the third symptom of one missing capability, not a new problem. The other two are already recorded, as deferred gaps, in prior ADRs:

- **ADR-0012's Consequences**: "a machine token can no longer claim `sender='owner'`... but it can still claim any *other* room member's `agent_name` as `sender`... Machine tokens in this system are global bearer credentials (`app/models.py`'s `Machine` has no per-room binding at all) deliberately not scoped to a single agent identity... Closing it would require binding machine tokens to room identities (a per-agent credential this system doesn't have) — a separate piece of work, deferred, not rejected."
- **ADR-0014's Consequences**: "a poll-triggered park notification cannot name the agent... without a broader, out-of-scope change to the poll endpoint's contract" — because `GET /v1/rooms/{id}/messages` (`app/routers/rooms.py`) carries no identity beyond the caller's bearer token.

All three trace to the same root cause: a `RoomMember` (a room seat) is not bound to any specific agent identity. Any valid machine token can post as any member of any room, indefinitely, by design — `app/rooms.py`'s `post_message` docstring says so plainly ("machine tokens are deliberately not bound to one agent identity in this system, so the membership check just below remains the only, and sufficient, guard for that case"). The incident is what that gap looks like when the wrong agent is the one holding a valid token and a copy-pasted brief.

**This is a revision of the original proposal, made before any of it was built, after two owner corrections:**

1. **Claim-on-first-write alone still lets a wrong agent legitimately claim a seat by posting first** — the exact race that motivated this ADR in the first place. A pure claim-on-first-write design converts an *indefinite* impersonation gap into a *one-shot* one, which is real progress, but it does not remove the race: if the wrong agent (the one the incident was about) posts before the right one connects, its token becomes the legitimate holder of that seat, and the *right* agent is the one locked out. The owner asked for a way to close the race entirely for rooms where they can plan ahead: **pre-assigning a seat to a specific, already-registered machine at room-creation time**, so the wrong agent is refused on its very first message, not after it has already claimed something.
2. **The original draft's "same machine, two tabs share one token" limitation is factually wrong for this deployment.** Verified directly against the live `machines` table (read-only query, 2026-09-10): the owner registers a **separate machine token per agent, not per host**. Two pairs make this unambiguous:
   - `Rankati - Commander LXC109 - Capital NUC` (id `01M06Y81M9CXH7NH69TRKFWSHW`, active) and `Rankati - Dev Ai LXC109 - Capital NUC` (id `01M05V6ZG2SM4B8FG2C8PQFZNP`, active) — two distinct, separately-minted machine rows for two different agents running on the *same* LXC container (`LXC109`, Capital NUC). (A third row with the same name as the first, id `01KZEBQTP66D1VAXQPC8VEQ54Q`, is `revoked` — a re-minted replacement for that same agent, not evidence of a second live token for it.)
   - `7rf.ae LXC 112` (role `commander`, id `01M1S199BPY9XAFBTDKQP03HTD`) and `7rf.ae - builder LXC 112` (role `builder`, id `01M20BDYNDW7XYXJDEB6AVNSFV`) — the same pattern: two agents, two tokens, one physical container.

   A machine token in this deployment therefore already identifies exactly one agent, not "whichever agent happens to be running on that box right now." This changes what seat binding actually closes (see decision 9) and retires the old "two tabs, one token, indistinguishable" limitation as not applicable here (see Consequences for what residual limitation, if any, replaces it).

The owner and the assistant settled the decisions below — this revision — to close this gap as far as it can actually be closed for this deployment, and to be explicit about the parts that still can't.

## Decision

### Layer 1 — the join prompt announces its target, before anything else

1. **A new paragraph, placed before even `intro`, is the first thing a joining agent reads.** `generate_room_join_prompt` (`app/onboarding.py`) currently opens with `intro` ("You're joining a live chat room I run..."), followed by the ADR-0014 owner-open-gate paragraph (`_room_open_gate_policy_block`, placed "AHEAD OF EVEN" the file-policy block per that function's own docstring) and then the ADR-0012 file-policy block. This ADR adds one more paragraph and puts it ahead of *all* of them, including `intro` itself — a step further than either precedent, because the mismatch has to be caught before the agent absorbs *any* room-specific framing as this session's new task, and `intro` itself already states room-specific facts ("You are '{agent_name}'; the other participant is '{partner_name}'") that presume the reader is the right agent.

   Content, built from what a `Room` actually carries. Decision 12 below adds an optional `project` field to `Room` specifically so this block can state a precise, comparable fact instead of only a room name/topic an agent has to eyeball — this is the concrete fix for the gap the original draft left open ("there is no `project` field on `Room` to read"). The block states the room's own identity (name, id, `project` if set, `group_name` if set, `topic` if set, and the full member list) and directs the agent to compare that against *its own* current work — which the agent knows and the server does not:

   - **When the room has a `project` set:** "This room's stated project is '{project}'. Compare that, exactly, against the project you are currently working on. If it does not match exactly, STOP: do not join this room, do not act on anything below this line, and tell your operator immediately."
   - **When the room has no `project` set:** the same STOP framing, but honestly scoped to a judgment call rather than an exact-match claim it can't back up: "This room has no stated project. Compare its name/topic below against what you are currently working on, using your own judgment. If this doesn't look like your work, STOP..."

   Full block text (verbatim, `project` case):

   > STOP AND CHECK BEFORE READING ANY FURTHER. This join prompt is for room "{room.name}" (id {room_id}), project: "{project}"{, group "{group_name}"}{, topic: "{topic}"}. Members: {member list}. It would join you as '{agent_name}'. This room's stated project is '{project}' — compare that, exactly, against the project you are currently working on. If it does not match exactly, STOP: do not join this room, do not act on anything below this line, and tell your operator immediately that you were pasted a join prompt for a different project.

   No-`project` case:

   > STOP AND CHECK BEFORE READING ANY FURTHER. This join prompt is for room "{room.name}" (id {room_id}){, group "{group_name}"}{, topic: "{topic}"}. Members: {member list}. It would join you as '{agent_name}'. This room has no stated project — compare its name and topic above against what you are currently working on, using your own judgment. If this doesn't look like your work, STOP: do not join this room, do not act on anything below this line, and tell your operator immediately that you were pasted a join prompt for a different room/project.

   Rationale: nothing server-side can prevent the paste itself — once the text is in a tab it is in that agent's context — so the only real defence is the agent recognising the mismatch at message one, before it acts. Follows the briefing discipline ADR-0014 decision 2 and ADR-0012 decision 9 already established ("agents are briefed, not just refused" — brief so a compliant agent never needs a refusal to learn the rule), extended one position further up the prompt because this check, uniquely, gates whether the agent should read the rest at all.

2. **Honest limitation: this is instruction, not enforcement.** It reduces the blast radius of a misdirected paste — a compliant agent stops before acting — but it cannot prevent the paste, and it cannot un-paste anything already read. See Consequences.

### Layer 2 — a room seat binds to a machine, either assigned at creation or claimed by the first machine that writes to it

3. **A `RoomMember` (a room seat) binds to exactly one `Machine`, via one of two paths, both feeding the same `bound_machine_id` column:**

   - **Assignment (new in this revision), optional, at room-creation time.** The owner may pick a specific, already-registered, active machine for either or both seats when creating a room — a dropdown listing active machines (decision 13 below) next to each agent-name field. An assigned seat's `bound_machine_id` is set immediately, before any message is ever posted. From that moment, only that machine's token may post or attach as that member — including the *very first* message. This is what actually closes the race the original draft left open: the wrong agent, if it posts at all, is refused outright, not one-shot-claimed-ahead-of-the-right-one.
   - **Claim-on-first-write (the original mechanism, kept as the default/fallback).** A seat the owner leaves unassigned starts with `bound_machine_id = NULL` ("open") and binds to the first machine token that successfully posts or attaches as that member — exactly as the original draft specified, for exactly the same three reasons given there: (a) it needs no separate `POST /v1/rooms/{id}/join` call — one fewer moving part, one fewer thing a briefing can fail to mention; (b) it matches this codebase's existing precedent for "first qualifying write sets a fact" (`Room.opened_at`, ADR-0014, set by the first `sender == "owner"` commit, not a separate "open" call); (c) it preserves the property that every existing room and every room created through the v1 API without the new optional field keeps behaving exactly as it always has — **assignment is opt-in, never required**, so this is additive, not a breaking change to any existing integration.

   Both paths write the same column and are enforced by the same check (decision 5): "is `bound_machine_id` set, and if so, does it match the caller's machine?" An assigned seat simply starts already-answered; an unassigned seat answers itself on first write. No second column, no "assigned vs. claimed" flag anywhere in the schema — the distinction is purely in *when* the column gets its value, not in what enforcement does with it.

4. **Storage: a new nullable column, `RoomMember.bound_machine_id: str | None`, FK to `machines.id`, indexed.** Added next to `RoomMember.side` (ADR-0007's per-seat column on this same table). NULL means "unclaimed and unassigned — open to the first machine that writes." Set once — at creation (assignment) or on first accepted write (claim) — and thereafter changed only by the owner's release/reassign action (decision 8).

5. **Enforcement point: under the room's row lock, in both places a message or a file can enter a room.**
   - `app/rooms.py`'s `post_message`: the existing sender-membership check (an *unlocked* pre-check, correct for a pure existence read) is unaffected. A seat *bind-or-check* is a write that must be race-free, so it runs under the room row lock — but, correcting an earlier draft of this decision, **not** at the same point `_check_close_as_agreed_gate` (ADR-0017) occupies, i.e. **not** before the insert retry loop. `_check_close_as_agreed_gate` stays exactly where it was: called once, immediately after the lock is acquired, before the retry loop begins (`app/rooms.py`, `post_message`) — it is a pure read-only gate (it raises or it doesn't; it never mutates anything), so running it once per call is correct as-is. The seat bind-or-check is different: it is a *write* (claiming an open seat sets `bound_machine_id`), and it runs **inside** `_insert_message_and_maybe_close` — the retried-as-a-unit function called *from* the loop, on every attempt, not once ahead of it. This mirrors why that same function also (re-)sets `room.opened_at` and the close-guardrail fields inside itself rather than once before the loop: an `IntegrityError` on the unique `(room_id, seq)` index rolls back the *entire* transaction, undoing a seat claim made during that attempt along with everything else in it. `check_and_bind_seat` re-derives the seat's current state fresh (its own query against the already-held-locked row, not a cached object) on every call, so redoing it inside the retried function means a retry always re-claims or re-checks correctly against the freshly-committed state instead of silently losing a claim an earlier, rolled-back attempt appeared to make. Putting it before the loop instead — where a one-shot, read-only gate like ADR-0017's belongs — would leave exactly that gap: a claim made on an attempt that then hits `IntegrityError` would vanish with the rollback but never be redone, since nothing on the next attempt would re-run it. This mirrors `switch_room_mode`'s own precedent for why `RoomMember` rows can be safely mutated once the *Room* row's lock is held without a separate lock on `room_members` itself: every mutator that touches `RoomMember` for a given room already serializes through that room's `FOR UPDATE`; seat binding follows the identical pattern rather than inventing a second lock.

     **Cosmetic consequence of the two gates sitting at different points, worth recording so it doesn't read as a bug later:** because `_check_close_as_agreed_gate` still runs first (before the retry loop) and `check_and_bind_seat` only runs afterward (inside the retried function), a `kind="done"` post from the *wrong* machine, in a debate/critique room that hasn't yet reached its consensus floor, surfaces `close_as_agreed_not_permitted` (ADR-0017) rather than `seat_bound_to_other_machine` (this ADR) — the read-only gate gets there first and raises before the seat check is ever reached. This is harmless: either error refuses the post outright and nothing is ever inserted, so the *outcome* (no message written, wrong machine refused) is identical either way — only the specific error code returned differs, and only for this one narrow combination (wrong machine, `kind="done"`, floor not yet met).
   - `app/attachments.py`'s `add_room_attachment` already acquires the room's row lock inside its own retry loop and checks membership right there — the seat bind-or-check is added at that same point, under the same lock, on every retry attempt (idempotent: re-checking an already-matching binding on a retry is a no-op).

   Because `app/rooms.py` imports `app/attachments.py` (for `delete_room`'s blob-reclaim call) and not the reverse — the exact circularity `_sender_is_member`'s own docstring already documents — the bind-or-check logic is **not** duplicated by hand in both files. It lives in a small new shared module, `app/room_seats.py`, with one function: `check_and_bind_seat(db, room, sender, principal) -> None`. Both `app/rooms.py` and `app/attachments.py` import it; it imports neither, sitting below both.

   `check_and_bind_seat`'s logic: no-op if `principal.kind != "machine"` (decision 6). Otherwise look up the `RoomMember` row for `(room.id, sender)` — a plain, direct query under the already-held room lock, same reasoning `_sender_is_member` gives for not importing `app.rooms.get_members`. If no such member exists, no-op (the pre-lock membership check in the caller already rejects a non-member `sender` before this function is ever reached). If `bound_machine_id` is `NULL`, set it to `principal.machine.id` — the claim. If `bound_machine_id` is already set and matches `principal.machine.id`, no-op — the ordinary case of the seat's bound (or assigned) machine posting again. If it's set and does **not** match, raise `ApiError(403, "seat_bound_to_other_machine", ...)` — the refusal (decision 9 gives the verbatim wording).

   **A third content-entry point, found only during implementation:** `app/attachments.py`'s `add_attachment_from_brain_document` ("Attach from Brain") links an already-saved Brain document into a room — no new bytes, but a genuine `sender`-attributed write, under its own room-row lock and its own copy of the sender/membership check (same circularity reason `_sender_is_member` is duplicated rather than shared). This wasn't one of the two paths named when this ADR was first drafted; it is exactly the same shape as `add_room_attachment`'s upload path, so it gets the identical `check_and_bind_seat` call, at the identical point (right after the membership check, inside its own retry loop, before anything is written).

6. **The owner is never subject to seat binding — keyed on `principal.kind`, not on the `sender` string.** ADR-0014 decision 6 and ADR-0017 decision 6 both establish this posture for their own gates, keyed on `sender == "owner"`. This ADR is keyed one level more strictly: `check_and_bind_seat` no-ops whenever `principal.kind != "machine"` — i.e. whenever the request is authenticated with the owner token — regardless of which `sender` string the owner's own request happens to post as. Nothing today stops the owner's own token from posting *as* an agent's name if the owner chooses to (e.g. for testing); that path is deliberately excluded from seat binding, the same way it is already excluded from ADR-0017's consensus gate and ADR-0014's open gate — a constraint on agents, never on the owner's control of their own room.

7. **Reads stay open — binding applies to writes only.** ADR-0008 decision 1 deliberately allows any machine token to read/poll any room (the observer pattern). This ADR does not touch that. `poll_messages` and the message/room list endpoints read no `sender` at all today and continue to read none; `bound_machine_id` is written only by `post_message` and `add_room_attachment`, via `check_and_bind_seat`. Stated explicitly so the two ADRs do not appear to contradict: ADR-0008 opened reads; this ADR gates writes; neither reaches into the other's territory.

8. **The owner can release or reassign a seat's binding — one action, not two.** The original draft proposed a release-only action ("clear, then let the next write claim it") and rejected a direct-rebind action as unneeded complexity. Now that assignment is itself a first-class, owner-driven action at create time (decision 3), the same capability mid-room is the natural, symmetric counterpart — the owner should not have to clear a seat and then hope the right machine's next post wins whatever race is left. **New owner-only action:** `POST /v1/rooms/{id}/members/{agent_name}/seat`, body `{"machine_id": <str | null>}`, following the exact shape of `set_agent_uploads_allowed`/`set_requires_owner_open`: unlocked existence pre-check, room row lock, `room.status == "open"` guard (a closed room accepts no further posts of any kind regardless of binding), the mutation, and a `kind='system'` announcement in the same commit.
   - `machine_id: null` — **release**: clears `bound_machine_id`, same effect the original draft's release action had. The seat is open again; the next write from *any* machine token, as that member, claims it (identical to a brand-new room's seat).
   - `machine_id: "<id>"` — **reassign**: directly sets `bound_machine_id` to that machine (which must exist and be `status == "active"`, same validation assignment-at-creation uses, decision 13), bypassing the "clear, then hope" indirection entirely. This is the recovery lever the incident itself calls for: a machine gets re-minted, or the owner wants to swap which agent holds a seat mid-room, without a window where the seat sits open to whichever token happens to post next.

   Both branches post a `kind='system'` announcement naming the seat and stating the new state (open, or bound to a named machine) so the room's other participant — and any agent that re-reads the transcript — sees the change, following this codebase's "agents are briefed, not just refused" discipline for every other mid-room toggle.

### Assignment and the project field, together

9. **What this closes, precisely — reassessed against the corrected per-agent-token fact.**
   - **Assignment (decision 3, first bullet) closes ADR-0012's Consequences gap (a) completely, for any seat the owner chooses to assign — no carve-out.** Because the seat is bound before any message exists, a different machine's very first attempt to post or attach as that member is refused. There is no window in which the wrong agent can win a race, because there is no race: the assignment already answered "which machine" before either agent's first message could arrive.
   - **Claim-on-first-write (decision 3, second bullet — the default for an unassigned seat) closes the same gap only from the moment of first claim onward**, exactly as the original draft described: before any claim, the seat is still open to whichever machine token posts as that member *first* — including a wrong one. That is a narrower, one-time version of the old gap (an impostor gets one shot, not indefinite repeat access, and afterward the *legitimate* agent is the one who gets refused and has to ask the owner to release or reassign the seat) — not a full closure. This is exactly the residual risk the owner's first correction (see Context) asked this revision to give them a way to opt out of, via assignment.
   - **Re-assessing ADR-0012's Consequences gap (a) in light of per-agent tokens:** the original draft's closure claim for an *already-claimed* seat did not actually depend on whether tokens are per-agent or per-host — binding to a specific `Machine` row is already finer-grained than "any machine token may post as any member," regardless of how many agents share that token. What the per-agent-token correction changes is how much that closure is *worth* in practice: because this owner's tokens already identify one agent each (Context, point 2), a bound (or assigned) seat's "only this machine's token may post as this member" guarantee is, in this deployment, equivalent to "only this agent may post as this member" — not merely "only this physical host." The original draft's own honest hedge (only closes it "down to the credential this system has, which is per-machine, not per-agent") turns out to already be per-agent in the deployment that actually matters here.
   - **Re-assessing ADR-0017's second Consequences gap ("separate NAMES, not separate ACTORS" — one token satisfying its own debate/critique consensus gate by posting both required objections itself):** the original draft said seat binding does *not* close this, because "a single machine legitimately running two separate agent processes and a single machine impersonating two separate agents are indistinguishable at the credential this system has." That reasoning assumed a machine token could legitimately run more than one agent. It does not, in this deployment (Context, point 2) — so the honest answer changes:
     - **When both of a room's seats are assigned to two *different* machines (decision 3, first bullet), this ADR now closes ADR-0017's gap too**, for exactly the same reason it closes ADR-0012's: a token authorized only as the machine assigned to seat A is refused outright the moment it tries to post as seat B's `agent_name` — it cannot single-handedly satisfy both members' objection requirements, because it cannot legitimately hold both seats at once.
     - **When one or both seats are left unassigned (claim-on-first-write), the structural possibility remains**: nothing stops one machine from being the first to claim *both* seats (post as agent-a, then post as agent-b) if it gets there before anything else does — `check_and_bind_seat` constrains "which machine may act as this member," not "how many members this machine may act as." What the per-agent-token correction changes here is not the mechanism but the *signal*: because this owner does not legitimately run two agents off one token, two `RoomMember` rows in the same room ending up with the identical `bound_machine_id` is not an ambiguous, expected outcome of shared infrastructure the way the original draft assumed — it is a concrete, actionable anomaly the owner can now trust and act on (e.g. via the seats panel, decision 14) precisely because their real fleet doesn't do that legitimately. Full enforcement of "no, this specific machine may not hold two seats in one room" is still not built (nothing rejects it outright), and is left as a documented, deferred follow-up in Consequences — but the value of even just *seeing* it changed materially with this correction.
   - **Still enables, does not by itself deliver, ADR-0014's Consequences gap (b) — naming the parked agent.** Unchanged from the original draft: `poll_messages` still takes no `principal`/`machine_id` parameter, so naming the parked agent in an owner ntfy ping still requires threading identity through the poll endpoint's contract — the exact API-surface change ADR-0014's own Alternatives Considered section weighed and declined for that ADR. This ADR still only makes a narrower, identity-based version of that idea *available* to a future ADR; it does not spend that cost itself.

10. **Existing rooms need no backfill, for either new column.** `bound_machine_id = NULL` is the literal "unclaimed and unassigned" state — every seat has always behaved this way, so leaving all pre-existing rooms' seats unbound blocks nothing that would have gone through before this ADR. `Room.project = NULL` is likewise the literal "no stated project" state — every pre-existing room already has no project field to read (the column didn't exist), so NULL is exactly what every existing room already "had," and the Layer 1 join-prompt block's no-`project` branch (decision 1) is written specifically so a room with `project IS NULL` gets a coherent, honest prompt, not a broken one. The owner's fleet, re-checked directly against the live database while writing this revision (2026-09-10): 47 rooms, 2 open, 45 closed (up from 32 rooms/1 open at the time of the original draft — the fleet keeps growing, which is itself a reason this migration must not assume any particular count). Neither column needs a data migration: this is a single additive migration (next free number, 0019) adding two nullable columns (`rooms.project`, `room_members.bound_machine_id`) with an indexed FK on the latter — no `UPDATE` statements at all.

11. **Backfilling existing rooms' seats to whichever machine most recently (or most often) posted as each member — still rejected, same reasoning as the original draft.** Before this ADR, nothing recorded which machine posted any given message as a given `sender`, so any such guess is unverifiable and could confidently bind a seat to the *wrong* machine, actively creating the lockout this ADR exists to make recoverable rather than merely leaving the seat open as it always was.

### The `project` field (new in this revision)

12. **`Room.project: str | None` — an optional, free-form (not `projects`-registry-FK) field, so the Layer 1 target check can compare an exact fact instead of asking an agent to eyeball a room name/topic.** The original draft's Layer 1 block was honest about a real weakness: "an agent can verify 'am I working on project X' precisely, but 'does this topic look like my work' is a judgement call" — because `Room` had nothing more precise than `name`/`topic`/`group_name` to offer, none of which is guaranteed to be (or even resemble) the Brain project name the agent already knows itself by from its own bootstrap. The owner agreed to close that gap with a dedicated field.

    **Design choice: free-form text, not a foreign key to `projects.name`.** Two designs were weighed:
    - A `ForeignKey("projects.name")`, mirroring `Deposit.project`/`Event.project`/etc. — guarantees the value is always a real, registered project name.
    - Free-form text, mirroring `Room.group_name` exactly (ADR-0008 decision 3: "Free-form labels (not tied to Brain projects) per the owner's choice", same table, same author, same reasoning).

    Free-form wins, for reasons specific to *this* field's actual job, not just precedent-matching:
    - **The exactness the join-prompt check needs comes from using the literal registered project name as the stored value, not from a DB constraint enforcing it.** An agent's own "what project am I on" fact already comes from the Brain's project registry (bootstrap). If the owner types that same canonical string into a room's `project` field, a plain string comparison in the join prompt is already exact — an FK adds no precision the UI's own autocomplete (decision 13) doesn't already deliver by construction.
    - **Rooms are not always about a project that exists in the registry yet.** A debate room stood up to plan a brand-new piece of work, before its first deposit ever auto-stubs the project, is a normal, legitimate use — `projects` rows are themselves auto-created lazily "on first mention of an unknown project name by a deposit" (`app/models.py`'s `Project` docstring), i.e. the registry is deliberately not the source of truth for "what projects exist to talk about," only for "what projects have been deposited to." Forcing an FK here would mean either pre-registering a project before a room about it could even be created, or silently auto-stubbing a `projects` row from room creation — a side effect this field's owner-facing, advisory purpose doesn't warrant.
    - **Consistency with this exact table's own, already-owner-approved precedent.** `Room.group_name` sits on the same table, was added for a related-but-distinct purpose (grouping, ADR-0008), and was deliberately kept free-text over the owner's own stated preference against Brain-project coupling. Introducing a second room-level field with the opposite (FK) posture, on the same table, for a reason that (per the point above) doesn't actually need the FK to work, would be an unjustified inconsistency.

    Validated the same shape as `_validate_group` (`app/rooms.py`): trimmed, blank-after-trim treated as "no project," length-capped (255 characters, matching `Project.name`'s own column width, so a room's `project` value is always at least *storable* as a real project name even though it isn't required to already be one). Accepted at room creation (`RoomCreateRequest.project`) and surfaced everywhere the room's other identity facts already are — `RoomCreateResponse`, `RoomListItem`, `RoomDetailResponse`, the room view header, and (decision 1) the join prompt's new target block. No mutator exists to change it mid-room — same posture `topic`/`mode` have outside `switch_room_mode`'s deliberate exception, and consistent with `project` being a room-identity fact fixed at creation, not a live-toggleable setting.

### UI: seat assignment and reassignment

13. **The create-room form gains two optional "Assign to machine" dropdowns, one per agent slot, listing only `status == 'active'` machines.** Sourced from a new `app/machines.py` helper, `list_active_machines`, filtering out `revoked` machines — necessary correctness, not just tidiness: the live `machines` table has at least one case (`Rankati - Commander LXC109 - Capital NUC`) where a `revoked` row and an `active` row share the exact same display name (a re-minted replacement for the same agent). Filtering to `status == 'active'` before rendering the dropdown removes the revoked duplicate entirely, so the owner is never shown two identically-named, ambiguous options — the active one is simply the only one listed. Each dropdown defaults to "— unassigned (open) —"; leaving it there is the unassigned/claim-on-first-write path (decision 3, second bullet), unchanged from every room created before this ADR. The same helper backs the v1 API's equivalent optional field, `RoomCreateRequest.seats: dict[agent_name, machine_id]`.

14. **The room view gains a "Seats" panel** showing each member's current binding state (open/unclaimed, or bound to a named machine) and a per-seat form (dropdown of active machines + Update) that posts to the release/reassign action (decision 8). Selecting "— unassigned (open) —" releases the seat; selecting a machine reassigns it. Owner-only, same `require_ui_session` posture as every other control on this page; hidden/disabled once the room is closed, matching every other mid-room toggle here.

### Copy-button labels use the real agent name (independent fix, same page)

15. **`room_view.html`'s per-participant "Copy join prompt" buttons currently fall back to a generic "Agent 1"/"Agent 2" ordinal whenever a room has no sides (freeform, collaborate, brainstorm) — even though the member's actual `agent_name` is already in scope in the very loop that renders the button.** This was never intentional obfuscation, just an oversight the sides-only case never got the same treatment as the labeled case. Fixed as part of this ADR's UI work (touching the same template the seats panel above lands in): the button label is now the side label when one exists (unchanged for debate/critique/asymmetric rooms), or the member's own `agent_name` when it doesn't (replacing the ordinal) — and, when that seat is currently bound to a specific machine (assigned or claimed), the bound machine's name is appended in parentheses, e.g. `Copy join prompt — Commander (Rankati - Commander LXC109 - Capital NUC)`. Machine names are owner-authored but rendered through ordinary Jinja2 autoescape only, same discipline as every other untrusted-but-owner-supplied string on this page (member names, `group`, `topic`) — never `|safe`.

## Alternatives Considered

- An explicit `POST /v1/rooms/{id}/join` claiming call, instead of claim-on-first-write for the unassigned/default path — rejected, same reasoning as the original draft: one more step an agent has to remember and one more place a briefing can fail to mention, for no change in the actual security property once a seat is genuinely unassigned. (Assignment, this revision's actual fix for the race, works entirely at create time — it needs no join call either.)
- Binding to something finer-grained than a machine (a specific agent process or session) — still rejected for this ADR: no such identity exists anywhere in this system (`Principal`/`Machine` model one bearer token per machine, full stop). Given the corrected per-agent-token fact (Context, point 2), this owner's actual fleet makes "per machine" and "per agent" coincide in practice, which is most of why this ADR is now worth shipping without that finer-grained credential — but the schema still only models per-machine, and a deployment that *did* share tokens across agents would not get this ADR's full benefit. Closing that in general remains a separate, larger piece of work (a per-session credential this system has never had), deferred, not rejected.
- An owner action to rebind a seat directly to a specific new machine id, instead of only clearing it — the **original draft rejected this** as unnecessary complexity ("clear-then-reclaim-on-next-write gets to the same end state... without the owner ever having to look up or type a machine id by hand"). **This revision reverses that call**: now that assignment is itself a normal, owner-driven, look-up-a-machine-id action at create time (decision 3, surfaced via a dropdown, decision 13), the mid-room equivalent (decision 8) is the natural symmetric counterpart, not an extra concept — and direct reassignment closes a real gap the clear-then-hope path left open (a window where the seat is open to whichever token posts next, not necessarily the intended replacement).
- A `ForeignKey("projects.name")` for `Room.project`, instead of free-form text — considered and rejected; see decision 12 for the full reasoning (the exactness the join-prompt check needs comes from what string is stored, not from a DB constraint; rooms legitimately predate a project's first deposit; and it would be an unjustified inconsistency with `group_name`'s already-settled, owner-approved posture on this exact table).
- Backfilling existing rooms' seats to whichever machine most recently (or most often) posted as each member — still rejected; see decision 11 (unchanged from the original draft's reasoning).
- Re-opening ADR-0014's Alternatives Considered decision to thread `sender`/identity through the poll endpoint's contract, so the park notification could always name the agent — not revisited here, unchanged from the original draft.

## Consequences

- **Schema/migration: additive, nullable, low-risk.** Two new columns — `rooms.project` (nullable text, indexed) and `room_members.bound_machine_id` (nullable FK to `machines.id`, indexed) — no data migration, no backfill (decision 10). Verified upgrade/downgrade/re-upgrade against a throwaway database seeded with rows shaped like the live fleet (32 rooms, 1 open, several machines both active and revoked) before this ADR's implementation landed.
- **What a wrong-tab paste still costs, even with every layer.** Layer 1 (decision 1) asks a compliant agent to stop *before acting*; Layer 2 (decisions 3-9) refuses a *write* from the wrong token, either immediately (an assigned seat) or after one claim (an unassigned seat). Neither undoes the one thing that has already, unavoidably, happened by the time either layer can act: the pasted text is now sitting in the receiving agent's context window. No server-side control — this ADR included — can retroactively scrub an agent's context or prove it was never read. Best case, every layer works exactly as designed and the wrong agent never posts a single message or reads a single attachment as a room member; the paste itself is not something Brainard can undo.
- **The honest limit of what this ADR achieves against the incident that motivated it, stated plainly: the observer pattern (ADR-0008) means the wrong agent's first read is never gated, at all, by anything built here.** `GET /v1/rooms/{id}/messages` (`poll_messages`) and the room list/detail reads require no membership today and still don't after this ADR (decision 7) — any machine token, wrong seat or not, may poll and read a room's *entire* transcript, repeatedly, with zero interaction with `check_and_bind_seat`. That means a careless wrong agent that reads before it ever tries to write — which is the ordinary sequence for an agent that joins a room and polls it, the exact shape ADR-0008's observer pattern was built to support — can absorb the full transcript into its context window before its first *write* is ever refused by Layer 2, and before Layer 1's own stop-and-check paragraph (decision 1) has stopped anything, if the agent doesn't act on it. **The write refusal this ADR adds does not, by itself, contain context contamination.** It stops the wrong agent from *acting* as a room member — posting, attaching — but it does nothing to stop the wrong agent from *reading*. The only thing that actually prevents contamination is the wrong agent voluntarily obeying Layer 1's instruction to stop before reading any further, which is instruction, not enforcement, and is therefore unenforceable: nothing server-side can tell a compliant read from a non-compliant one, or force the latter to stop. This is not a gap this ADR failed to close by oversight — no version of Layer 2 (write-side seat binding) can close a read-side gap, because reads were deliberately left open by a prior, still-load-bearing decision (ADR-0008), and re-closing them is a different, larger change this ADR does not make. Anyone relying on this ADR to fully contain a misdirected paste should read this bullet as the reason it doesn't: it reduces the blast radius of a *write*, not of a *read*, and the incident that motivated this ADR is a read-then-act incident, not a write-only one.
- **The observer pattern (ADR-0008) cannot be used to satisfy or evade anything seat binding is meant to prevent** — i.e., reading grants no *posting* privilege of any kind, before or after this ADR, and nothing about the read-side gap above lets a wrong agent bypass `check_and_bind_seat` on a write. This is a narrower, different claim than the bullet above: it says the read-side gap doesn't get worse because of this ADR, not that this ADR closes it.
- **Interaction with the incident scenario, spelled out plainly, now split by whether the owner used assignment.** If the owner assigned both seats at creation and Layer 1 fails (the wrong agent reads the prompt and posts anyway despite the new opening paragraph), the wrong agent is refused outright — its token was never the assigned one, so it never claims anything, and the *legitimate* agent connects normally. If the owner left the seat unassigned and Layer 1 fails, the original draft's failure mode still applies: the wrong agent's token claims the open seat, and the legitimate agent is the one who then hits `seat_bound_to_other_machine` and has to ask the owner to release or reassign it (decision 8). Both outcomes are a strict improvement over no seat binding at all (a loud, actionable refusal instead of silent, indefinite impersonation); assignment is strictly better than the unassigned fallback for a room the owner can plan ahead for, which is exactly why it's offered as the opt-in path rather than forced on every room.
- **One machine holding two seats in the same room is still not rejected outright.** Nothing in `check_and_bind_seat` stops a single machine from legitimately claiming (or being assigned) both of a two-member room's seats — the check is per-seat ("does this seat's bound machine match"), not per-room ("has this machine already bound a different seat here"). Given the corrected per-agent-token fact (decision 9), this owner's real fleet has no legitimate reason for that to happen, so it is now a meaningful, actionable anomaly rather than an expected, ambiguous outcome of shared infrastructure — visible on the seats panel (decision 14) as two identical `bound_machine_id` values. Actually rejecting it outright (a "one machine, one seat per room" constraint) was not requested by the owner for this revision and is left as a documented, deferred follow-up, not built here.
- **The "same machine, two tabs share one token" limitation from the original draft is retired, not fixed — it does not describe this deployment.** The original draft's Consequences section stated this as an unclosed gap; verification against the live `machines` table (Context, point 2) shows the owner already mints one token per agent, not per host, so two tabs on the same physical machine authenticate with two *different* tokens here, not one. This ADR does not claim to have solved the shared-token case for a deployment that *does* practice one-token-per-host — it simply no longer claims that limitation applies to *this* one, because it's been checked and doesn't.
- **The genuine residual limitation, for this deployment, is narrower: a seat's binding is only as good as the machine credential's own hygiene.** If a single registered machine's token is ever used, deliberately or by mistake, to drive more than one agent process at once (the owner's stated pattern is not to do this, but nothing in the schema prevents it), those two processes would be indistinguishable to seat binding, exactly the way two tabs on a shared token would be. This is a credential-discipline question for the owner's own fleet, not a schema gap this ADR could close differently — and it's a materially smaller residual risk than the one the original draft described, precisely because it depends on the owner doing something they don't currently do, rather than being baked into how every machine in the fleet already works.
- **Downstream, delivered by this ADR's implementation:** `app/room_seats.py` (`check_and_bind_seat`, imported by `app/rooms.py`'s `post_message` and `app/attachments.py`'s `add_room_attachment`/`add_attachment_from_brain_document`); `RoomMember.bound_machine_id` and `Room.project` (`app/models.py`) and their migration (0019); optional seat assignment threaded through `create_room` and `RoomCreateRequest`/`RoomCreateResponse`; the owner-only `POST /v1/rooms/{id}/members/{agent_name}/seat` release/reassign route and its `app/rooms.py` implementation; a new `403 seat_bound_to_other_machine` `ApiError`; the Layer 1 join-prompt target-check block and the `project`-aware rewording throughout `app/onboarding.py`'s `generate_room_join_prompt`; `app/machines.py`'s `list_active_machines`; the create-room and room-view UI (seat dropdowns, the Seats panel, the corrected copy-button labels); and the full test coverage listed in the implementation's own test files.
- **Not delivered by this ADR, left as documented follow-up:** threading polling-machine identity through `poll_messages`/`GET /v1/rooms/{id}/messages` so a park notification can name the waiting agent (ADR-0014 gap (b), decision 9) -- **closed by ADR-0020 decision 2**, which threads an `agent_name` query parameter through that endpoint for an unrelated reason (a "working" lease) and spends it on this gap too; a hard "one machine, one seat per room" constraint (this Consequences section, above) remains open.
