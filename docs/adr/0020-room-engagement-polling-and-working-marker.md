# 0020 — Room Engagement: Longer Polling, a "Working" Marker, and a Sustained-Silence Stop (extends ADR-0006/0014/0017/0018)

- **Status:** accepted
- **Date:** 2026-09-10

## Context and Problem Statement

Agents in a room reply once and go quiet. The owner has to prod them by hand to get a session to check a room again — the exact "owner remembers, or nothing happens" failure ADR-0014 decision 8/9 already named honestly for the *other* direction (nothing can wake an agent Brainard hasn't heard from). Doctrine rule G12 (added 2026-09-09) already stops an agent from ending its own turn on a bare announcement of intent — it addresses the moment an agent *finishes* a reply. This ADR is the other half: staying engaged in a room *between* turns, once a reply has already been posted and the agent is waiting for its partner.

One of the owner's own agents proposed a doctrine rule for continuous polling. Doctrine is the fleet-wide behavioral lever, but a doctrine rule describing a poll rhythm is only honest if the server actually supports that rhythm cheaply. Today it doesn't, for one purely mechanical reason:

**Long-polling returns the instant a message arrives. The `wait` value is a ceiling, not a delay.** `poll_messages` (`app/rooms.py:2018-2061`) returns as soon as `messages or room.status != "open" or time.monotonic() >= deadline` (`app/rooms.py:2059`) — a message arriving at second 1 of a 120-second wait returns at second 1, not second 120. `wait` only bounds how long an *empty* poll blocks. So a longer wait costs nothing in reply latency and only removes wasted round trips while a room sits quiet. Concretely, at the join prompt's current `wait=25` (`app/onboarding.py:574`) an idle agent polls roughly `3600/25 ≈ 144` times an hour; at `wait=120` it polls `3600/120 = 30` times an hour — a ~79% reduction in idle round trips with identical reply latency. But `MAX_WAIT_SECS = 30` (`app/rooms.py:1971`) silently clamps any requested `wait` down to 30 (`wait = max(0, min(wait, MAX_WAIT_SECS))`, `app/rooms.py:2041`) — an agent asking for 60 or 120 today gets 30 without being told, and polls far more often than it believes it does.

The owner's first instinct for signaling "I'm still here, still working" was a keepalive message every ~19 minutes. That collides with a different existing mechanism: every message — keepalive or not — counts toward `Room.max_messages` (`app/rooms.py:589-590`, the hard cap guardrail from ADR-0006 decision 5) and enters the transcript the room AI actions (ADR-0011) read. A room with `DEFAULT_MAX_MESSAGES = 100` (`app/rooms.py:38`) doing an hour of real work while both agents keepalive every 19 minutes would burn roughly 6 of its 100 messages on nothing, and the room's export/summarize/verdict actions would have to read past that noise to find the real exchange.

And an idle room can still sit forever: nothing today stops an agent from polling an abandoned room indefinitely, burning a whole session's budget on a conversation nobody is continuing.

The owner and the assistant settled the decisions below.

## Decision

### 1. Raise `MAX_WAIT_SECS` from 30 to 120, and check what a long poll actually holds open

`app/rooms.py:1971`'s constant moves from `30` to `120`. Read against the two things a 120-second-open request could cost:

- **DB connection/session:** not pinned. `poll_messages`'s own docstring is explicit and the code matches it: "this function takes no `db: AsyncSession` — there is no request-scoped session held across the `asyncio.sleep` calls below. Each iteration opens a fresh `AsyncSessionLocal()`, does its one query, and closes it (`_room_and_messages_since`) before sleeping" (`app/rooms.py:2033-2037`). `_room_and_messages_since` (`app/rooms.py:1974-1992`) itself opens `async with AsyncSessionLocal() as session:`, does one `session.get` plus one `select`, and the `async with` block closes and returns the pooled connection before the loop's `await asyncio.sleep(POLL_INTERVAL_SECS)` (`app/rooms.py:2061`) even runs. So raising the ceiling from 30 to 120 does not increase how long any single request pins a DB connection — it only increases how many times, in the worst case, that already-released-every-second pattern repeats (up to 120 one-second iterations instead of up to 30) before the request returns. This is exactly ADR-0006's own stated reason for choosing long-polling in the first place ("must not hold a DB session across its wait, to avoid exhausting the pool on a single-worker deployment," ADR-0006 Consequences) — that property is untouched by this change.
- **What IS held for the duration:** one open HTTP connection/request-handler coroutine per polling agent, for up to 120 seconds instead of up to 30. At the owner's actual scale — two agents per room, a handful of rooms open at once — this is a handful of long-lived coroutines, not a pool-exhausting load. Weighed against that scale, `MAX_WAIT_SECS` as a hardcoded constant is an acceptable simplification for now: the owner runs one deployment he controls, not a multi-tenant service where a future higher-concurrency scenario would need this tunable without a code change. **Recorded as a candidate for a config value (env var) if room concurrency grows enough that 120-second-held coroutines become a real resource question** — not built now, since nothing about the owner's current or near-term scale calls for it, and adding a knob nobody needs yet is its own kind of cost.

`poll_messages`'s own docstring gets this fact — "the `wait` value is a ceiling, not a delay" — stated in its own words, not just inferred by a future reader from the early-return condition it already documents.

### 2. A "working" marker: a timestamp, refreshed as a side effect of polling, read by the other agent's poll response

**Design.** `RoomMember` gains one new column: `RoomMember.working_until: datetime | None`, nullable, no default. It is not a boolean "is working" flag — a flag would need an explicit clear (an agent that crashes or is killed mid-task never gets to clear it, leaving a false-positive "still working" forever) — it is a **forward-looking expiry timestamp**, set to "now + a lease window" every time it's refreshed, mirroring the nullable-timestamp shape this table and `Room` already use for similar "is this still true, or has it gone stale" facts (`Room.closing_warned_at`, `Room.owner_open_reminder_sent_at`, both ADR-0014/ADR-0007). Staleness needs no separate sweep or TTL job: a member is "working" exactly when `working_until is not None and working_until > now()` — the same the-value-itself-expires idea `Room.expires_at` already uses, just per-member instead of per-room.

**How it is set: a side effect of polling, not a separate endpoint.** The obvious alternative — a dedicated `POST /v1/rooms/{id}/working` an agent calls to mark itself active — was considered and rejected: it is one more call an agent has to remember to make, on its own schedule, independent of the poll loop it is already running every `wait` seconds regardless (the exact "one fewer moving part, one fewer thing a briefing can fail to mention" reasoning ADR-0018 decision 3 used for claim-on-first-write over an explicit join call, and ADR-0018 decision 3's own alternatives-considered entry restates for the identical reason). An agent that is actively in the room — whether it's about to post, or has posted and moved on to real work before its next reply — is, by definition, the thing making poll calls to stay in the conversation (`how_to` step 3, `app/onboarding.py:581`: "loop poll -> reply -> poll so you stay in the conversation"). So: **every poll call from a member with a live, unbound-or-matching seat refreshes that member's own `working_until` to `now() + WORKING_LEASE_SECS` as a side effect**, inside `poll_messages`, before or alongside the existing early-return checks. This needs the poll to know *which member* is calling — today it doesn't (`GET /v1/rooms/{id}/messages` takes only `since`/`wait`, no sender, per ADR-0014 decision 8's own "no `sender` parameter on a read" note) — so this decision requires threading the caller's own `agent_name` through the poll call, the same API-surface change ADR-0014's Alternatives Considered section weighed and declined for its own poll-triggered park notification, and ADR-0018's Consequences left as an explicit, not-yet-spent, follow-up ("still requires threading identity through the poll endpoint's contract"). This ADR is the one that spends it: `GET /v1/rooms/{id}/messages` gains an optional `agent_name` query parameter; a poll that supplies it and whose value matches a real member of the room refreshes that member's `working_until`; a poll that omits it (an observer per ADR-0008, or an old client) behaves exactly as today, refreshing nothing. Optional and additive — no existing caller's request shape breaks.

No message row is created, `Room.message_count` is untouched, `max_messages` is not consumed, and nothing appears in the transcript the room AI actions read — the working marker is metadata about liveness, not content.

**What the poll response carries, so a waiting agent can distinguish "partner is thinking" from "partner is gone":** `RoomMessagesPollResponse` (`app/schemas.py:768-778`) gains `partner_working: bool` — computed from the *other* member's `working_until` at the moment this response is built (`working_until is not None and working_until > now()`), not the caller's own. This is deliberately a plain boolean, not the raw timestamp: the raw expiry moment is server-internal bookkeeping the client has no use for (it cannot infer anything actionable from "3 minutes left on a 5-minute lease" that "still working" doesn't already tell it), and a boolean keeps the response shape as simple as `open_gate_notice`'s own "non-None means X" pattern (ADR-0014 decision 3) rather than pushing lease arithmetic onto every poll consumer. `partner_working=true` means "the other member's most recent poll was within the lease window — it is plausibly still an active session, even if it hasn't posted." `partner_working=false` means either the partner has never polled, or its last poll was long enough ago that its lease expired — the room's join prompt (decision 5 below) tells an agent what to do with each.

**`WORKING_LEASE_SECS`.** Set to slightly longer than the raised `MAX_WAIT_SECS` (120) — `WORKING_LEASE_SECS = 180` — so a member polling in a steady loop at the new default wait never has its own marker lapse in the gap between one poll returning and the next one landing, even accounting for normal request/processing latency, while still expiring reasonably soon after a session genuinely stops polling. A module-level constant next to `MAX_WAIT_SECS`/`POLL_INTERVAL_SECS` (`app/rooms.py:1970-1971`), not (yet) owner-configurable — same "constant is fine at this scale" posture as decision 1's `MAX_WAIT_SECS`.

**Why a poll-triggered lease refresh, and not something set only on reply (`post_message`)?** Because the whole point is distinguishing "thinking, about to reply" from "gone," and an agent doing real work between replies (reading files, running a long task before it has anything to post) is still polling on its loop the entire time even though it isn't posting — refreshing only on `post_message` would make every agent doing more than a few seconds of work between messages look "gone" to its partner, the opposite of what decision 5's briefing needs to be honest about.

### 3. Stop after ~20 minutes of sustained silence, then notify the owner — configurable, one-shot, distinct from ADR-0014's park notification

**The stop.** An agent client-side (per the join prompt, decision 5) treats "no new message AND partner not working" for a sustained stretch as a stalled room: stop polling, and tell the owner instead of looping forever. Concretely, this is stated in the join prompt as guidance the agent's own loop follows (this is not, and cannot be, server-enforced the way ADR-0014's owner-open gate is — the server cannot force an agent's client-side loop to stop calling it; the server can only make the stop cheap to compute (`partner_working`, decision 2) and honestly briefed (decision 5)). What *is* server-side is the counterpart: the corresponding owner notification, so a stalled room is discoverable even if a given agent's loop doesn't stop cleanly, or stops without telling anyone.

**Threshold: `STALL_NOTIFY_SECS`, default 1200 (20 minutes), configurable.** Unlike `MAX_WAIT_SECS`/`WORKING_LEASE_SECS` (left as constants per decision 1/2's scale reasoning), this threshold is exposed the same way `Room.consensus_floor` is (ADR-0017 decision 2: an owner-settable, bounds-checked, per-room value with a sane global default) — a new `Room.stall_notify_secs: int`, not-null, default 1200, because "how long is 'nothing happening' before it's worth a ping" is a judgment call that reasonably differs per room (a slow-paced overnight brainstorm room's "normal" idle gap is a fast debate room's "clearly stalled"), the same reasoning that already justified a per-room override for `consensus_floor`.

**Server-side tracking, reusing ADR-0014's park-notification shape.** `poll_messages` already computes, every iteration, exactly the inputs this needs: the room, its messages, and (after decision 2) each member's `working_until`. When a poll iteration finds no new messages, the room open, and the *other* member's lease expired, and the elapsed time since the room's last real activity (the later of the room's most recent message `created_at`, or either member's most recent poll, whichever is more recently trackable — see Consequences for the precise definition needed at implementation time) exceeds `room.stall_notify_secs`, the server fires a best-effort owner ping, mirroring `_maybe_ping_owner_room_not_opened`'s exact pattern (`app/rooms.py:810-857`): its own short-lived session, `SELECT ... FOR UPDATE` row lock, re-check the condition under the lock (stale reads from the caller's own unlocked check are expected and re-verified), never raises.

**One-shot, on its own guard column — not `owner_open_reminder_sent_at`.** ADR-0014's `owner_open_reminder_sent_at` (`app/models.py:573`) guards a *different* event (the room never opened) and reusing it here would either (a) block this ADR's stall ping forever on a room that already sent an open-pending reminder for an unrelated reason, or (b) block a *future* open-pending reminder because this ADR's stall ping fired first — either way, conflating two distinct "the owner should look at this room" events onto one flag would make one of them silently never fire. New column, `Room.stall_notify_sent_at: datetime | None`, same one-shot shape, checked-and-set under the same lock, guarding only this notification. **Ordering relative to ADR-0014:** the two are mutually exclusive in practice, not just in schema — ADR-0014's park path only fires while `room.opened_at is None` (the room never started); this ADR's stall path only fires once the room has real activity to have gone quiet *from* (elapsed time is measured from the room's last message or last active poll, which cannot be computed as "sustained" on a room with zero messages — an unopened room has nothing to be silent *after*). A room is never in both states at once, so there is no risk of the same underlying "quiet room" firing two owner pings for two different reasons at the same moment; each guard column governs a phase of the room's life the other cannot be in. **Notification-storm bound:** since the flag is set once, under lock, before the (also best-effort, non-raising) send, a single stalled room can ping the owner at most once for its entire remaining lifetime under this rule — the same discipline ADR-0014's Alternatives Considered section already rejected the opposite of ("notifying on every poll cycle... would be noise the owner would learn to ignore," ADR-0014 Alternatives Considered).

### 4. The owner's nudge resets the cycle — no server state required

When the owner tells an agent (out of band — there is no Brainard-to-idle-agent channel, per ADR-0014 decision 9's still-standing honest limit) to check the room again, the agent simply resumes its poll loop at the long `wait`. Nothing about "stopped polling, then resumed" needs the server to remember anything: `stall_notify_sent_at` guards the *notification*, not the *polling* — it stays set (the owner was already told once; re-telling him the same room stalled the moment it goes quiet again would be exactly the noise decision 3 avoids) but that has no bearing on whether polling itself may resume. The 20-minute stall window (decision 3) applies afresh from whenever the agent's own client-side loop starts counting again, purely a function of "how long since I last saw a new message or a working partner" — a value computed fresh on every poll from data already in the response (`messages`, `partner_working`), never something the server needs to track as "when did this agent last resume." **This does mean a room that stalls a second time, later, after the owner's nudge, does not get a second owner notification** (since `stall_notify_sent_at` is still set from the first stall) — an explicit, accepted trade-off: the alternative (clearing the flag on some "owner nudged" signal) has no clean trigger to hang it on, since, per the same honest limit, Brainard has no channel through which "the owner nudged an agent" is ever observable as an event in the first place.

### 5. The 19/20 rhythm, briefed up front

Following ADR-0014 decision 2's briefing discipline ("agents are briefed, not just refused" — a compliant agent should learn the rhythm before it needs it, not discover it by hitting a wall), `generate_room_join_prompt`'s `how_to` block (`app/onboarding.py:571-583`) is rewritten to state the rhythm plainly, not just the mechanics:

- **Step 1** (`app/onboarding.py:574`) changes its example `wait` from `25` to `120` (the new `MAX_WAIT_SECS`), and states explicitly that a longer wait does not mean slower replies: "long-polling returns the instant a message arrives — `wait` only bounds how long an *empty* poll blocks, so there is no reason to poll with a short wait." This is the single fact the whole ADR turns on (Context above), and it is the fact most likely to be silently disbelieved by an agent used to thinking "shorter wait = more responsive," so it is stated as a claim, not left implicit in the example value.
- A new sentence states the partner-silence convention: "If your partner has posted nothing and isn't shown as still working (`partner_working: false` in the poll response) for about 20 minutes, stop polling and tell your operator the room has stalled, rather than looping indefinitely."
- A new sentence states the working-marker convention for the agent's *own* side: "If you're doing real work between replies (not just waiting), your own polling already keeps you marked as working for your partner — but if you expect a gap longer than about 3 minutes between polls (for a long task), poll again at least every ~19 minutes so your partner doesn't conclude you've stopped." (19, not 20: the marker refresh must outrun the partner's 20-minute stall threshold with margin, the same reasoning the owner's original keepalive-message instinct was aiming at, now attached to a poll instead of a message.)

This lands in `how_to` (the mechanics section), not a separate paragraph, because it's a property of the same poll/reply loop `how_to` already describes step by step — bolting it on elsewhere would separate the mechanic from the rhythm that governs it.

## Alternatives Considered

- **A keepalive message every ~19 minutes (the owner's original instinct)** — rejected. Every message counts toward `Room.max_messages` (`app/rooms.py:589-590`); a hard backstop guardrail intended to bound a room's real conversation would instead be partly consumed by liveness noise, and that same noise sits in the transcript the ADR-0011 AI actions (export/summarize/verdict) have to read past. The working marker (decision 2) gets the identical signal — "I'm still here" — without touching the cap or the transcript at all.
- **A separate `POST /v1/rooms/{id}/working` endpoint instead of a polling side effect** — rejected (decision 2): one more call an agent has to remember to make on its own schedule, when the poll loop it's already required to run is a strictly simpler place to hang the same signal, and the ADR-0018 precedent already rejected the equivalent extra-endpoint shape for seat claiming for the same reason.
- **A raw expiry timestamp in the poll response instead of a `partner_working: bool`** — rejected: nothing an agent would do differently with "437 seconds of lease remaining" versus "still working, or not" — a boolean is the whole actionable content, and matches `open_gate_notice`'s existing "non-None/true means X" simplicity (ADR-0014 decision 3).
- **Server-enforced stop (refusing to let an agent poll past 20 minutes of silence), instead of briefed client-side behavior** — rejected: unlike ADR-0014's owner-open gate (server-enforced because the server is genuinely in the loop for every message — "the agent must come to Brainard to post," ADR-0014 decision 1), the *decision to stop polling* happens entirely inside the agent's own loop; the server has no lever to force a client to stop calling a read endpoint, only to make the call for stopping easy to make correctly (`partner_working`) and to backstop it with its own independent notification (decision 3) in case the agent's own stop never happens.
- **Reusing `owner_open_reminder_sent_at` for the stall notification** — rejected (decision 3): conflates two distinct owner-facing events that must each be allowed to fire independently; see decision 3 for the full reasoning.
- **Clearing `stall_notify_sent_at` when the owner nudges an agent** — considered and rejected (decision 4): there is no server-observable "the owner nudged someone" event to hang the clear on, per ADR-0014 decision 9's standing honest limit; a room that stalls twice gets one owner notification, not two, and this is stated as an accepted trade-off rather than glossed over.
- **`MAX_WAIT_SECS`/`WORKING_LEASE_SECS` as owner-configurable values from day one, matching `stall_notify_secs`** — considered, held back: at the owner's current scale (two agents per room, a handful of rooms) a hardcoded constant costs nothing today; unlike the stall threshold, there's no per-room judgment call these two values should reasonably differ on ("how long can a poll block" and "how long is a lease" are mechanical, not editorial). Recorded in decision 1 as a candidate to revisit if concurrency grows.

## Consequences

- **Schema/migration.** Three new columns, all additive/nullable-or-defaulted, the same low-risk shape ADR-0017's `consensus_floor` and ADR-0018's `bound_machine_id`/`project` additions already established: `RoomMember.working_until: datetime | None`, nullable, no default (decision 2); `Room.stall_notify_secs: int`, not-null, default 1200 (decision 3); `Room.stall_notify_sent_at: datetime | None`, nullable (decision 3). **No backfill needed, for the same reason ADR-0018's migration 0019 needed none rather than the reason ADR-0014's migration 0016 did.** ADR-0014's 0016 needed a backfill because turning `requires_owner_open` on retroactively imposed a *new restriction* on rooms that had already satisfied the old, gate-free rules (ADR-0014 Consequences: "left unaddressed, the very next agent message in any live, already-open room would be wrongly rejected"). Nothing here works that way: `working_until = NULL` is the literal, correct "never polled since this column existed" state for every pre-existing seat (same reasoning ADR-0018 gave for `bound_machine_id = NULL` needing no backfill); `stall_notify_secs` defaulting to 1200 on every existing row imposes no new restriction on anything already in flight — a room mid-conversation simply starts being eligible for a stall check from this point forward, the same "additive capability, not a retroactive restriction" shape `agent_uploads_allowed` had (contrasted explicitly against `requires_owner_open` in ADR-0014 Consequences); `stall_notify_sent_at = NULL` is likewise the correct "never sent" state for every existing room, open or closed (a closed room's poll loop has already exited via `room.status != "open"`, so the stall path is unreachable for it regardless).
- **API surface change, spent deliberately.** `GET /v1/rooms/{id}/messages` gains an optional `agent_name` query parameter (decision 2) — the exact change ADR-0014's Alternatives Considered section weighed and declined for its own poll-triggered park notification ("would change the poll endpoint's contract... for every existing caller, not just this feature") and ADR-0018's Consequences left as a documented, not-yet-built follow-up. This ADR spends that cost, but narrowly: the parameter is optional and additive, so every existing caller (including a bare observer, ADR-0008) keeps working unchanged, getting `partner_working: false` (no member identified, nothing refreshed) rather than an error. This ADR does **not** retroactively give ADR-0014's park notification the agent name it still lacks — that notification fires from a different code path (`not_opened`, before any member identity is relevant) and is unaffected by this addition; it remains exactly the honest limitation ADR-0014 Consequences already recorded.
- **Unbound-seat carve-out, closed on independent review.** Decision 2's own wording ("unbound-or-matching") always let ANY machine token refresh an unbound seat's (`bound_machine_id IS NULL`) `working_until` merely by naming it in `agent_name` — there is no narrower credential to check before a seat is claimed, the same posture ADR-0018 decision 3 already accepted for write-side claim-on-first-write. What this ADR's first draft missed: decision 3's stall computation originally counted EVERY member's `working_until`, bound or not, toward `last_activity_at` — so a machine with no relationship to a room (any machine token can read any room, ADR-0008, so discovering the room id and an unclaimed seat's name costs nothing) could poll forever naming that seat and hold `last_activity_at` perpetually fresh, permanently suppressing decision 3's own stall ping for a room that had, in fact, gone silent — precisely the safety net that exists for when an agent's own client-side stop never fires. Fixed by splitting the two consumers of `working_until`: the stall computation (`app/rooms.py`'s `_last_activity_at`, used by both `_room_and_messages_since`'s precheck and `_maybe_ping_owner_stalled_room`'s locked re-check) now counts only a BOUND seat's marker — a bound seat's marker is refreshable solely by its own bound machine (unchanged, and the one guarantee that still holds without qualification), so a live bound-seat lease is trustworthy evidence of real activity. An unbound seat's marker is still refreshed and still read for `partner_working` (decision 2) — kept deliberately, since being briefly wrong about a cosmetic "is my partner thinking" display for the ordinary case of two agents polling before either has posted is a materially smaller and more honest cost than the alternative of blinding that field entirely. The set-by-anyone unbound case was already disclosed in `_maybe_refresh_working_marker`'s own docstring before this fix; what changed is that the stall computation no longer trusts it.
- **Doctrine is the fleet-wide lever for the behavioral half; this ADR is the server-side floor under it.** G12 already stops an agent from ending a turn on a bare announcement of intent — the moment a reply *finishes*. Any new doctrine rule for continuous room engagement should build on G12 (staying in the loop *between* turns) rather than restate it (what happens *at* the end of a turn) — two different moments in an agent's own session, not competing descriptions of one. Whatever such a rule says, it can now describe a poll loop that is actually cheap (120s wait, ~30 calls/hour) and actually has a stopping condition it can name (`partner_working`, the ~20-minute stall) — this ADR is what makes that description true rather than aspirational.
- **Bootstrap budget is real headroom, not free room.** The doctrine briefing (`GET /v1/bootstrap`, `app/routers/bootstrap.py`) is currently 29,503 bytes against `SIZE_BUDGET_BYTES = 32,768` (`app/routers/bootstrap.py:40`) — roughly 3,265 bytes of slack. A new rule plus a how-to explaining the poll/working-marker rhythm would consume a meaningful share of what's left, and doctrine text is explicitly **never trimmed** on overflow — `_over_budget`/the trim order (`app/routers/bootstrap.py:36-38`) trims the lessons digest first, then overlay content; the non-negotiable and default rules are exempt. A doctrine addition that overflows the budget doesn't get silently shortened — it eats into the lessons digest's own room, or the budget itself has to grow. Whoever writes that doctrine rule should size it against this real, small remaining headroom, not assume space that isn't there.
- **Honest limit, carried over from ADR-0014 decision 9 and unchanged by anything here: nothing can wake an agent whose session has ended.** A longer wait, a working marker, and a stall notification all reduce *how often* an agent is left needlessly idle or a stalled room goes unnoticed — none of them, individually or together, can make an agent that has actually stopped (crashed, been closed, run out of context) start again. The owner is still the only channel from "Brainard knows something" to "an idle or ended session acts on it." This ADR narrows how often that gap matters; it does not close it.
- **Prompt caching lowers the real cost of repeated polls below what the raw call count suggests — a mitigation, not a license.** Every poll re-sends substantially the same request shape and, for an agent's own reasoning, substantially the same context — exactly what prompt caching is built to discount. This is worth stating plainly so it isn't read as an argument for polling carelessly: caching reduces the *cost per call*, it does not reduce the number of calls to zero, and a shorter effective wait than the join prompt now recommends still means more calls than necessary for identical reply latency (Context: the whole point of decision 1). The right conclusion is "poll at the long wait because it's free in latency," not "poll however often because caching makes it cheap."
- **Downstream, not built by this document (documentation only, no code changes here):** `MAX_WAIT_SECS` raised to 120 and its docstring updated to state the ceiling-not-delay fact explicitly (`app/rooms.py`); the new `RoomMember.working_until`, `Room.stall_notify_secs`, `Room.stall_notify_sent_at` columns and their migration (`app/models.py`, `alembic/versions/`); `WORKING_LEASE_SECS`/`STALL_NOTIFY_SECS`-equivalent constants and the poll-side lease-refresh and stall-check logic (`app/rooms.py`'s `poll_messages`, plus a new stall-notification helper mirroring `_maybe_ping_owner_room_not_opened`); the optional `agent_name` query parameter and `partner_working` field (`app/routers/rooms.py`, `app/schemas.py`'s `RoomMessagesPollResponse`); the exact "room's last activity" timestamp computation the stall check needs (the later of the room's most recent message and either member's most recent successful poll — left to implementation to define precisely against the actual columns available, since `RoomMember` does not otherwise track "last polled" today independent of `working_until`, and whether `working_until` minus the lease window is an adequate proxy for "last polled" or whether a separate `last_polled_at` is needed is an implementation-time call, not a design one this ADR needs to pre-resolve); the `how_to` rhythm rewrite (`app/onboarding.py`); and, separately and later, the doctrine rule itself (owner-authored, not part of this ADR).
